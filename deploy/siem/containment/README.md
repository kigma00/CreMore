# 외부 수신기의 침해 감시·증적 보관

기존 [SIEM 이벤트 계약](../../../docs/SIEM_INTEGRATION.md)을 사용한다. 별도 CreMore
서비스나 새 전송 프로토콜을 추가하지 않는다. 아래 Splunk 예시는 수신기가 Splunk일 때만
적용한다. 다른 SIEM은 같은 시간·연속성 조건을 해당 제품의 예약 규칙으로 옮긴다.

수신기 관리자는 CreMore 배포/DB 관리자와 분리한다. 전송 토큰은 **수집 전용**, 해당 설치의
전용 index/sourcetype에만 허용하고 search/delete/관리 권한을 주지 않는다. 설치 구분은
이벤트의 사용자 제어 문자열 대신 수신기의 token→index 설정으로 고정한다. 예시는 한 설치를
`index=cremore_audit`로 받는 경우다. 여러 설치를 같은 검색으로 합쳐 생존 여부를 판단하지 않는다.

[`savedsearches.conf`](savedsearches.conf)의 규칙을 수신기에서 검토해 설치한다. 미수신은
수신 시각 `_indextime`으로 판단하여 앱이 보낸 미래 시각이 경보를 억제하지 못하게 한다.
5분 생존 신호 기준 12분(2분 전달 여유), 시간당 앵커 기준 125분(5분 여유)에 경보한다.
주기를 바꾸면 규칙 기준도 맞춘다. 30일 검색창은 예시 보존기간이며 최초 미수신도
`stats` 결과의 null을 검사해 경보한다. 연속성 검색은 event_id 재전송을 중복 제거하고
anchor_no로 정렬한다. 지연 도착은 먼저 경보하고 이전 누락이 도착하면 다음 평가로 해소한다.
anchor 번호가 같은데 내용이 다르면 충돌도 별도로 경보한다. 경보 통지 수신자는 수신기에서
지정한다. 이 파일은 실제 알림 주소나 외부 전송을 만들지 않는다.

보관은 외부 계정의 수정 불가 저장소에 수신기 관리자 권한으로 export한다. S3를 쓰면 별도
계정의 Object Lock **COMPLIANCE** retention과 bucket versioning을 설정하고 retention을
단축할 권한을 CreMore에 주지 않는다. 다른 제품은 동등한 WORM 기능을 사용한다. 수신기
전송/보관 실패도 수신기 자체에서 감시한다. 기간은 회사의 증적 보존 정책에 따라 정하고
시험용 데이터를 먼저 넣어 읽기·삭제 거절·만료 정책을 검증한다. immutable retention을
실제 운영에 적용하는 것은 비용과 되돌릴 수 없는 기간이 있으므로 별도 운영 변경이다.

적용 후 검사: 새 설치 이벤트가 도착하는지 확인하고, 별도 테스트 index에서 생존 신호 중단,
앵커 누락/번호 되돌림/동일 번호 충돌/체인 상태 이상과 중복 재전송을 검증한다. 실제 앱의
감사 행은 수정·삭제하지 않는다. 공격자가 서명/HMAC 키를 가진 프로세스로 새 이벤트를
위조하거나 SIEM ingest token으로 정상 생존 신호를 보내는 것은 이 규칙만으로 방지할 수 없다.
독립 공급자 감사 로그·네트워크 격리·워크로드 신원 회수를 병행한다.

저장된 앵커의 seq/MAC를 기존 `/api/v1/audit/integrity` 조회와 대조할 수 있지만 침해된
API의 응답만 신뢰하지 않는다. 복구한 DB의 검증 결과와 외부 보관본을 함께 비교한다.
