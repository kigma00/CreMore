## 요건

CreMore는 오픈소스로 배포되고 도입 기업의 모양을 미리 알 수 없다. 담당자가 한 명인
스타트업부터 보안팀이 있는 대기업까지, Vault를 이미 쓰는 곳과 도입하지 않은 곳까지 전부
있다. 로컬 평문 보관을 줄이는 것이 목표다. 현재 구현이 모든 배포에서 디스크 부재를
보장하지는 않는다. 환경변수는 Docker 설정·서비스 관리자·호스트 백업에 남을 수 있다.
`/api/v1/settings/local-credentials`는 `PROCESS_CONFIGURATION`만 관측하며
`disk_persistence: UNKNOWN`을 반환한다. 메모리 캐시·이전 복호화 키도 함께 고려해야 한다.

## 1. 지금 로컬에 남는 것

| 항목 | 위치 | 누구 | 수명 |
|---|---|---|---|
| `API_ADMIN_TOKEN` | `.env` | 1인 | 무기한 · 회전 경로 없음 |
| `OIDC_CLIENT_SECRET` | `.env.public` | 팀 | 무기한 (IdP 발급) |
| `OIDC_COOKIE_SECRET` | `.env.public` | 팀 | 무기한 |
| `FINGERPRINT_KEY` | `.env` | 전부 | 무기한 · **회전 불가** |
| `POSTGRES_PASSWORD` | `.env` | 전부 | 무기한 (내부 전용) |
| 공급자 토큰 | DB (봉인) | 전부 | 공급자에 달림 |
| AWS SSO 캐시 | `~/.aws` | 1인 | 단기 (약 1시간) |

### 가장 큰 문제

`FINGERPRINT_KEY` 하나가 **두 일을 겸했다**. 지문 keying은 회전하면 안 되고(저장된 대조가
전부 고아가 된다), 봉인 마스터키는 회전해야 한다. 모순된 요구가 한 값에 묶여 있었고,
봉인 형식 `sealed:v1:<...>`에 키 식별자가 없어 두 키 공존도 불가능했다.

결과: `.env` 하나가 새면 DB 안 모든 공급자 토큰이 열리고, 바꿀 방법이 없었다.

## 2. 원리

장기 토큰을 저장해야 하는 공급자(GitLab PAT · Notion · Confluence · Bitbucket)가 있는 한
키는 필요하다. 요건은 "키를 없애라"가 아니라 **"키의 뿌리를 로컬 디스크 밖에 두라"** 이며,
둘 곳은 넷뿐이다.

| 뿌리 | 로컬에 남는 것 | 무인 재시작 | 다중 replica |
|---|---|---|---|
| Vault / OpenBao | 경로·인증 설정; 가져온 키는 프로세스 메모리 | 인증 경로가 유효할 때 | 동일 뿌리 설정 시 |
| 클라우드 KMS | 암호문·키 ID; 복호화 키는 프로세스 메모리 | 워크로드 권한이 유효할 때 | 동일 뿌리 설정 시 |
| OS 키체인 | 키체인 및 컨테이너에 전달한 환경 | 기존 컨테이너는 환경 재사용 | 동일 키 배포 시 |
| passphrase | 프로세스 환경; Docker 설정에 남을 수 있음 | 기존 컨테이너는 환경 재사용 | 동일 문구·salt 배포 시 |

다섯 번째가 있다 — **애초에 봉인하지 않는 것**. `vault://` 참조만 쓰면 봉인 키 자체가
필요 없다. 지금도 되지만 봉인 저장이 기본으로 보여서 잘 쓰이지 않는다.

## 3. 설계: 봉인 키 뿌리를 선택 가능하게

구현된 순서는 이렇다. `SEALING_KEY_SOURCE` 같은 열거형은 만들지 않았다 — **무엇을
설정했는지가 곧 선택**이고, 하나 더 두면 둘이 어긋날 수 있다.

```
1. vault       SEALING_KEY_VAULT_PATH   무인 재시작 ○ · 다중 replica ○
2. kms         SEALING_KEY_CIPHERTEXT   무인 재시작 ○ · 다중 replica ○
3. passphrase  SEALING_PASSPHRASE       주입 경로에 따라 보관 위치가 달라짐
4. env         SEALING_KEY              주입 경로에 따라 보관 위치가 달라짐 · 회전 가능
5. (없음)      FINGERPRINT_KEY 파생      지문 키와 복호화 뿌리가 결합됨 → 화면이 경고
```

밀려난 뿌리는 **열쇠고리에 남아 계속 연다.** 그래야 뿌리를 옮겨도 옮기기 전에 봉인된
자격증명이 고아가 되지 않는다.

키체인(④)은 이 순서에 없다. 컨테이너가 OS 키링에 닿을 수 없어 호스트에서 꺼내
`SEALING_KEY`로 넘기기 때문이다 — 즉 4번으로 들어온다. 무엇을 쓰고 있는지는 ⑧ 화면이
말해준다.

### ① 봉인 키 분리 + 키 식별자 (완료)

봉인 형식에 **어떤 키로 봉인했는지**가 들어간다.

```
sealed:v1:<base64url(nonce || ciphertext)>                 (읽기만, 새로 쓰지 않음)
sealed:v2:<key_id>:<base64url(nonce || ciphertext)>        (새 봉인)
```

`key_id`는 마스터에서 HKDF로 뽑은 16진수 16자다. 키 자체의 해시가 아니라 KDF 출력이므로
식별자에서 키를 역산할 수 없다.

| 설정 | 뜻 |
|---|---|
| `SEALING_KEY` | 새 봉인에 쓰는 키. 비우면 `FINGERPRINT_KEY`에서 파생한다 |
| `SEALING_KEY_PREVIOUS` | 쉼표로 구분한 이전 키들. **열기만** 하고 새로 쓰지 않는다 |

**기존 설치는 아무것도 바뀌지 않는다.** `SEALING_KEY`를 설정하지 않으면 지금까지와 같은
마스터를 쓰고, `sealed:v1:`은 계속 열린다. 달라지는 것은 새 봉인이 v2로 나가면서 어떤
키를 썼는지 기록된다는 점뿐이다.

**이것이 여는 것**

- **회전이 가능해진다.** `SEALING_KEY`를 새 값으로 바꾸고 옛 값을 `SEALING_KEY_PREVIOUS`에
  남기면, 저장된 토큰은 계속 열리면서 새 봉인은 새 키로 나간다.
- **②~⑥이 가능해진다.** 키 출처를 바꾸는 일은 곧 마스터를 바꾸는 일이고, 키 식별자 없이는
  바꾼 뒤에 무엇이 어느 키로 봉인됐는지 알 수 없다.
- **`FINGERPRINT_KEY`가 토큰 마스터키가 아니게 된다.** `SEALING_KEY`를 따로 두면
  `FINGERPRINT_KEY`는 지문 keying만 한다. `vault://` 참조만 쓰는 설치라면 봉인 키가
  아예 필요 없다.

**열리지 않을 때** 오류가 키 식별자를 말한다(`SEALING_KEY_NOT_AVAILABLE: <id>`). 어느 키가
없어서 못 여는지 운영자가 알 수 있어야 하기 때문이다. 키 식별자는 비밀이 아니다.

### ② KMS 봉투 암호화 (완료)

마스터를 AWS KMS에 두고, 로컬에는 **암호문만** 남긴다. `.env`나 DB 사본을 통째로
가져가도 그것만으로는 아무것도 못 연다. 암호문을 마스터로 되돌리려면 해당 CMK에 대한
`kms:Decrypt`가 필요하고, 그 권한은 이 프로세스가 이미 실행 중인 워크로드 신원
(EC2 인스턴스 프로파일 · ECS 태스크 역할 · EKS IRSA · 운영자의 `aws sso login` 세션)에
붙지, 옆에 놓인 파일에 붙지 않는다.

| 설정 | 뜻 |
|---|---|
| `SEALING_KMS_KEY_ID` | 암호문을 여는 CMK. 비밀 아님 |
| `SEALING_KEY_CIPHERTEXT` | KMS가 만든 데이터 키의 암호문. 비밀 아님 |
| `SEALING_KEY_CIPHERTEXT_PREVIOUS` | 쉼표 구분. **열기만** 하고 새로 쓰지 않는다 |

만드는 법 — 평문 키가 KMS 밖에 **한 번도 존재하지 않는다**:

```
aws kms generate-data-key-without-plaintext \
  --key-id <cmk> --key-spec AES_256 --query CiphertextBlob --output text
```

**설계에서 정한 것**

- **CMK를 명시한다.** `Decrypt`는 암호문만으로도 되지만 `KeyId`를 같이 보낸다. 그래야
  다른 CMK로 만든 암호문으로 바꿔치기해도 조용히 열리지 않고 KMS가 거절한다.
- **`kms:Decrypt` 외에는 호출할 수 없다.** 다른 스캐너 클라이언트와 같은
  `readonly_client`로 감싼다. 워크로드 신원에 무슨 권한이 있든 이 경로는 Decrypt뿐이다.
- **32바이트 미만이면 거절한다.** 데이터 키가 아닌 것을 연 CMK라면, 약한 마스터로 전부
  봉인하느니 소리내어 실패하는 편이 낫다.
- **오류는 고정 코드만 낸다** (`SEALING_KMS_DECRYPT_FAILED: AccessDeniedException`).
  SDK 예외에 담긴 호출자 ARN 같은 세부는 전달하지 않는다.
- **캐시하지 않는다.** 호출 시점은 자격증명을 봉인할 때와 워커가 뜰 때뿐이고 스캔마다가
  아니다. 그 빈도면 묵은 마스터를 따지는 것보다 매번 부르는 게 단순하다.
- **기동 시에는 KMS를 부르지 않는다.** 형식만 검사한다(암호문 base64, CMK 동반 여부).
  연결이 전부 `vault://`인 워커는 봉인 키가 아예 필요 없으므로, KMS가 닿지 않는다고
  부팅까지 실패할 이유가 없다.
- **KMS로 옮겨도 `SEALING_KEY`는 열쇠고리에 남는다.** 빠지면 옮기기 전에 봉인된
  자격증명이 전부 고아가 된다.

**배포 경로**

| | 설정 위치 |
|---|---|
| Compose | `.env`의 `SEALING_*` (`docker-compose.yml`이 api·worker 양쪽에 전달) |
| Helm | `config.sealing.{kmsKeyId,keyCiphertext,keyCiphertextPrevious}` |
| Helm (16진수 마스터) | `applicationSecret.{sealingKey,sealingKeyPrevious}` — Secret의 키 이름 |

Helm에서 암호문은 평문 값으로 두고 16진수 마스터는 Secret 참조로만 둔다. 암호문은
CMK가 지키는 대상이라 비밀이 아니고, 마스터는 비밀이기 때문이다. 다중 replica가
필요한 대기업이 쓸 경로는 이쪽이다 — 모든 replica가 같은 마스터를 받고, 노드에는
아무것도 남지 않는다.

Vault를 이미 쓰면서 KMS는 안 쓰는 조직이라면, External Secrets Operator로
`applicationSecret.sealingKey`가 가리키는 Secret 키를 Vault에서 채우는 것으로 지금도
같은 결과를 낼 수 있다. ③은 이것을 CreMore가 직접 하게 만드는 일이다.

### ③ Vault를 봉인 키 뿌리로 (완료)

이미 Vault/OpenBao를 쓰는 조직이면 마스터를 거기 두면 된다. `SECRET_STORE_MOUNT`
아래 KV v2 경로에, 필드 하나가 32바이트 이상을 16진수로 담는다.

```
vault kv put secret/cremore/sealing-key key="$(openssl rand -hex 32)"
```

| 설정 | 뜻 |
|---|---|
| `SEALING_KEY_VAULT_PATH` | 마스터가 있는 KV 경로 |
| `SEALING_KEY_VAULT_FIELD` | 그 시크릿 안의 필드 이름. 기본 `key` |
| `SEALING_KEY_VAULT_PATH_PREVIOUS` | 쉼표 구분. **열기만** 하고 새로 쓰지 않는다 |

**API도 저장소에 붙는다 — 여기만.** 지금까지 시크릿 저장소는 워커 전용이었다.
연결의 `vault://` 참조를 푸는 건 워커뿐이기 때문이다. 그런데 대시보드에서 입력한
토큰을 **봉인하는 건 API**다. 봉인 마스터를 Vault에 두면 API도 그 경로를 읽어야 한다.

그래서 권한을 나눴다.

| | 읽어야 하는 것 | 설정 |
|---|---|---|
| 워커 | 연결 참조 **+** 봉인 경로 | `SECRET_STORE_TOKEN` / `kubernetes.role` |
| API | 봉인 경로 **하나뿐** | `SEALING_VAULT_TOKEN` / `kubernetes.sealingRole` |

Helm에서는 컴포넌트별로 ServiceAccount가 따로 있으므로 Vault Kubernetes 역할도
따로 묶을 수 있다. `sealingRole`을 비우면 API가 워커 것을 그대로 쓴다 — 동작은 하되
API가 마운트 전체를 읽게 되므로, 권장하지 않는다.

**설계에서 정한 것**

- **32바이트 미만 · 16진수 아님 · 필드 없음은 전부 거절한다.** KMS 경로와 같은 이유다.
- **기동 시 저장소를 부르지 않는다.** 경로가 설정됐는데 저장소가 이 프로세스에
  설정돼 있지 않으면 그것만 기동 시 거절한다(형식 검사). 실제 읽기는 필요할 때다.
- **Vault가 KMS보다 앞선다.** 둘 다 설정한 설치는 어느 쪽을 믿는지 이미 말한 셈이다.
  밀려난 쪽은 열쇠고리에 남아 계속 열 수 있다.
- **워커의 Vault 배선을 한 군데로 모았다** (`kv_from_settings`). 설정에서 클라이언트를
  만드는 코드가 두 벌이 되면 한쪽만 고쳐지기 때문이다.

**Vault가 있으면 애초에 봉인을 안 해도 된다.** 토큰 자체를 Vault에 넣고 연결에는
`vault://` 참조만 두면 봉인 마스터가 아예 필요 없고, 이건 지금도 된다. ③은 "Vault는
있지만 담당자가 대시보드에 붙여넣는 방식을 쓰고 싶다"는 경우를 위한 것이다.

### ④ OS 키체인 (완료 — 단, 설계가 바뀌었다)

**원래 설계는 불가능했다.** "컨테이너가 OS 키링을 읽는다"로 적었지만, 실제로는 안 된다.

| OS | 왜 안 되는가 |
|---|---|
| Windows | DPAPI는 Win32 API다. 컨테이너는 Linux VM이라 호출 경로가 없다 |
| macOS | Keychain은 Security.framework다. 마찬가지로 Linux VM에서 못 부른다 |
| Linux | D-Bus 소켓을 마운트하면 가능하지만, 데스크톱 세션이 떠 있어야 한다 |

세 OS 모두에서 동작해야 한다는 조건을 못 지킨다. 그래서 **호스트에서 꺼내
환경변수로 넘기는** 방식으로 바꿨다.

이게 성립하는 근거는 하나다 — **Compose는 쉘 환경을 `.env`보다 우선한다.** 확인했고,
`deploy/helm/tests/chart.test.cjs`가 그 우선순위를 테스트로 고정한다. Compose가 언제든
파일을 우선하도록 바뀌면, 조용히 `.env` 값으로 봉인하러 돌아가기 때문이다.

| OS | 보관 | 필요한 것 |
|---|---|---|
| macOS | Keychain (`security`) | 내장 |
| Linux | Secret Service (`secret-tool`) | libsecret-tools + 키링 세션 |
| Windows | DPAPI (`ConvertFrom-SecureString`) | 내장 |

Windows 예제는 DPAPI 암호문 파일을 남긴다. 다른 OS도 키체인 저장소가 있으며,
키를 컨테이너 환경으로 전달한 이후의 보관은 키체인과 별개다. 이전 문서의 DPAPI 왕복
기록은 당시의 관측이며 이번 리팩터링의 검증 결과로 사용하지 않는다.

키체인에서 값을 꺼내 새 컨테이너에 전달하려면 해당 OS 인증 경로가 필요하다.
기존 컨테이너의 재시작은 이미 주입된 환경을 재사용하므로 재입력을 요구하지 않는다.
쉘 변수를 지워도 Docker 설정에서 지워지는 것은 아니다. 따라서:

- **AWS를 쓰는 1인이라면 ②(KMS)가 더 낫다.** 무인 재시작이 되고 세 OS에서 동일하다.
- ④는 **AWS도 Vault도 없는 1인**을 위한 것이다.

명령은 README "5. (선택) 봉인 키의 보관 위치 분리하기"에 있다.

### ⑤ 기동마다 새로 생성 (완료 — 단, 프로세스 안이 아니다)

`API_ADMIN_TOKEN`은 배포자가 교체한다. 아래 명령으로 새 값을 생성해 컨테이너에
전달하면 `.env` 기록을 피할 수 있지만 Docker의 컨테이너 설정에는 남을 수 있다.

```
API_ADMIN_TOKEN="$(openssl rand -hex 32)" docker compose up -d
```

**프로세스가 스스로 만들 수는 없다.** 이 토큰은 `api`·`worker`·`web` 셋이 같은 값을
가져야 한다 — 대시보드 프록시가 이 값으로 API를 부르기 때문이다. API가 기동 시
생성하면 web은 그 값을 알 방법이 없다. 그래서 생성 지점은 **컨테이너 밖**, 운영자의
쉘이다. Compose가 쉘 환경을 `.env`보다 우선하므로 한 값이 셋에 모두 전달된다 —
④와 같은 근거이고, 같은 테스트가 고정한다.

**한계**

- 생성 명령을 다시 실행해 컨테이너를 재생성하면 값이 바뀐다. 기존 컨테이너의
  `restart`는 같은 값을 쓴다. 외부 호출 스크립트도 교체된 값을 공급받아야 한다.
- replica가 여럿이면 동일한 값을 일관되게 공급해야 한다. 팀 배포는
  `AUTH_MODE=oidc`를 사용하며 `deploy/compose/reverse-proxy`가 그 구성을 제공한다.

**`OIDC_COOKIE_SECRET`은 하지 않는다.** oauth2-proxy의 세션 쿠키 키라서, 기동마다
새로 만들면 재시작할 때마다 로그인한 사람 전원의 세션이 끊긴다. 팀 배포는 정의상
사람이 여럿이므로 이건 생성이 아니라 외부 주입(⑨의 Secret 경로)이 답이다.

### ⑥ 기동 시 passphrase (완료)

**④가 닿지 않는 곳이 있다.** SSH로만 쓰는 헤드리스 리눅스 서버에는 데스크톱 세션이
없어서 `secret-tool`이 못 뜬다. AWS도 Vault도 없다면 남는 건 하나 — **사람.**

```
read -rs -p "CreMore sealing passphrase: " SEALING_PASSPHRASE
export SEALING_PASSPHRASE && docker compose up -d && unset SEALING_PASSPHRASE
```

| 설정 | 뜻 |
|---|---|
| `SEALING_PASSPHRASE` | 기동 시 입력하는 문구. 최소 12자 |
| `SEALING_PASSPHRASE_PREVIOUS` | 쉼표 구분. **열기만** 하고 새로 쓰지 않는다 |

**설계에서 정한 것**

- **salt를 `FINGERPRINT_KEY`에서 파생한다.** 새 변수를 만들지 않고, 그 키는 애초에
  회전이 불가능하므로 안정성이 구조적으로 보장된다. 결과적으로 **문구만으로는 훔친
  DB가 안 열리고, 문구가 없는 `.env` 사본만으로도 안 열린다**. 다만 문구가
  컨테이너 설정이나 다른 운영 파일에 남아 있으면 그 보관 경계도 보호해야 한다.
- **scrypt n=2¹⁶ (약 240ms · 64MiB).** 자격증명을 봉인할 때와 워커가 뜰 때만 부르므로
  스캔 성능과 무관하다.
- **NFKC 정규화.** 같은 한글 문구도 자판·OS에 따라 바이트열이 달라진다. 정규화하지
  않으면 한쪽에서 만든 봉인이 다른 쪽에서 안 열리고, 이유를 말해주는 게 아무것도 없다.
- **12자 미만은 기동 시 거절한다.** 사람이 아직 자리에 있을 때 거절해야 더 긴 걸 칠 수
  있다. 구성 규칙은 두지 않는다 — 길이만 도움이 된다(NIST SP 800-63B).
- **Vault·KMS가 여전히 앞선다.** 그 둘은 무인 재시작이 되고, 설정한 설치는 이미 어느
  쪽을 원하는지 말한 셈이다. 밀려난 문구는 열쇠고리에 남아 계속 연다.
- **`SEALING_KEY`보다는 우선한다.** 선택 우선순위일 뿐, 문구가 환경변수보다
  안전하게 보관되었다는 증거는 아니다.

새 컨테이너에는 같은 문구를 공급해야 하고, 분실하면 해당 봉인 자격증명을 열 수 없다.
기존 컨테이너의 자동 재시작은 저장된 환경으로 가능하다. Vault·KMS를 사용해도
현재·이전 문구나 키가 설정에 남으면 이전 봉인을 열 수 있으므로 운영자가 함께 관리해야 한다.

### ⑦ 공급자 단기 경로를 온보딩 기본으로 (완료)

**Schema 2는 이미 강제하고 있었다.** 어댑터가 장기 자격증명을 아예 거절한다.

| 공급자 | 받는 인증 |
|---|---|
| GitHub | `github_app` **만** |
| GCP | `adc` · `workload_identity` **만**, `secret_refs` 금지 |
| Azure Key Vault | `workload_identity` **만**, `secret_refs` 금지 |
| GitLab · Atlassian | `bearer`/`basic` — 공급자가 단기 발급을 제공하지 않는다 |

**남아 있던 건 Schema 1 소스 연결이었다.** 온보딩이 "토큰 입력"을 먼저 내밀었고,
GitHub App을 쓰려면 비밀 저장소가 필요했다. 이유는 봉인 쪽이었다 — `seal_token`이
`token` 한 값만 담을 수 있는데, App은 셋이 함께여야 의미가 있는 값이다
(app id · installation id · private key).

봉투는 원래 JSON 객체였고 `seal_token`만 키가 하나여야 한다고 고집했을 뿐이다.
`seal_fields`로 일반화했고, `seal_token`은 그중 한 필드짜리 경우가 됐다. **워커는 한
줄도 안 바꿨다** — `inject_secret`이 이미 세 필드를 찾고 있었다.

**온보딩 기본이 바뀌었다.** GitHub을 고르면 폼이 App으로 열린다. 토큰 입력은 목록에
남지만 먼저 나오지 않는다.

- **PEM은 브라우저가 인코딩한다.** 사람에게 파일을 base64로 바꿔 붙여넣으라고 하면
  절반만 붙는 일이 생기고, 그러면 서버가 "invalid"라고 말하는 게 전부다.
- **세 값이 다 차기 전에는 등록 버튼이 잠긴다.** 반만 입력된 App으로 등록하면 아무것도
  저장되지 않고, 그 사실을 알려주는 건 첫 스캔이 된다.
- **연결 목록이 어느 방식인지 말한다** (`credential_source: "GITHUB_APP"`). 없으면 1시간
  만료 자격증명이 무기한 저장 토큰과 똑같이 보이고, 구별하려면 자격증명을 열어야 한다.

**남는 것.** GitLab · Notion · Confluence · Bitbucket은 공급자가 단기 발급을 제공하지
않는다(5절 참고). 그쪽은 봉인 마스터를 어디 두느냐(②~⑥)가 답이다.

### ⑧ "로컬에 무엇이 남는가" 화면 (완료)

②~④를 다 해도 **운영자가 그게 먹혔는지 확인할 방법이 없었다.** `SEALING_KMS_KEY_ID`를
설정한 것과 마스터가 KMS에 있는 것은 다른 문장이고, 그 차이는 누가 `.env`를 복사한
뒤에야 드러난다.

`GET /api/v1/settings/local-credentials` (관리자 전용)이 **실행 중인 프로세스가 부팅한
설정**을 읽어서 답한다. 소스 화면(공급자 연결 탭) 하단에 패널로 붙는다.

| 보고하는 것 | |
|---|---|
| 봉인 마스터의 뿌리 | `VAULT` · `KMS` · `ENVIRONMENT` · `FINGERPRINT_KEY` |
| 현재 봉인 키 식별자 | 16진수 16자. HKDF 출력이라 비밀이 아니다 |
| 항목별 | **이 설치가 값을 직접 보유하는지**(`held_here`), 회전 가능한지, 왜 그런지 |

질문이 "디스크에 있는가"가 아니라 **"값을 직접 보유하는가"**인 이유가 있다. 환경변수는
환경변수일 뿐이고, 그게 파일에서 왔는지 운영자의 쉘에서 왔는지(⑤) 시크릿 매니저에서
왔는지는 **실행 중인 프로세스가 볼 수 없다.** 말할 수 있는 건 값 자체를 들고 있는지,
아니면 다른 것 없이는 쓸모없는 참조만 들고 있는지(KMS 암호문·Vault 경로)뿐이다.

**두 가지 규칙을 지킨다.**

- **값은 절대 반환하지 않는다.** 설정됐는지 아닌지(boolean)뿐이다. 유일한 예외가 키
  식별자인데, 이건 "어느 키가 없어서 못 연다"는 오류가 이미 출력하는 값이다.
- **볼 수 없는 것은 말하지 않는다.** `OIDC_CLIENT_SECRET`은 oauth2-proxy 것이고 이
  프로세스에 주어지지 않으므로 목록에 없다. 일부만 조용히 빠진 목록은 아예 없느니만
  못하다.

뿌리를 **판별할 때는 아무것도 호출하지 않는다** (설정만 본다). 키 식별자를 말하려면
Vault/KMS를 불러야 하므로 그건 실패해도 `SEALING_ROOT_UNREACHABLE`로 보고하고 요청은
성공시킨다 — 상태 화면이 정작 필요할 때 안 뜨면 소용이 없다.

## 5. 없앨 수 없는 것

| 항목 | 이유 |
|---|---|
| `OIDC_CLIENT_SECRET` | IdP가 앱에 발급한 것. Vault/KMS에서 주입할 수는 있어도 없앨 수는 없다 |
| `FINGERPRINT_KEY` | 저장된 지문을 keying한다. 회전하면 대조가 전부 고아가 된다. **단 ① 이후로는 토큰 마스터키가 아니다** |
| `POSTGRES_PASSWORD` | 가능하지만 DB 볼륨과 어긋나면 못 붙는다. 외부 노출도 없다. 위험 대비 이득이 적다 |
| GitLab · Notion · Confluence · Bitbucket 토큰 | 공급자가 단기 발급을 제공하지 않는다 |

## 6. 도입 형태별 최종 모습

| | 1인 | 소수 | 팀 (중소) | 대기업 보안팀 |
|---|---|---|---|---|
| 배포 | Compose | Compose | Compose+OIDC 또는 Helm | Helm 다중 replica |
| 대시보드 인증 | ⑤ 기동마다 생성 | ⑤ | IdP | IdP |
| 세션 비밀 | — | 외부 주입 | 외부 주입 | **외부 주입 필수** |
| 봉인 뿌리 | ② / ④ / ⑥ | ② / ④ / ⑥ | ② / ③ | **② 또는 ③ 필수** |
| 공급자 | ⑦ | ⑦ | ⑦ | ⑦ |
| 가시성 | 전체 | 전체 | 전체 | **⑩ 필요** |

대기업은 **Vault나 KMS가 사실상 필수**다. replica 간 공유가 필요해 기동 시 생성을 쓸 수
없기 때문이다. 다행히 대기업은 둘 중 하나가 거의 항상 있다.

## 7. 대기업에서 추가로 빠진 것

① ~ ⑦이 끝나도 대기업에는 둘이 남는다.

- **⑨ 감사 로그 내보내기** — `/api/v1/audit`은 최대 1000건이며 전체 감사 스트리밍은 없다.
  신규 finding 발견은 별도 영속 대기열과 [SIEM exporter](SIEM_INTEGRATION.md)로 전달할 수 있다.
  이 이벤트는 전체 감사 이력이나 후속 상태 변경을 대신하지 않으며 자동 보존 기간 설정도 없다.
- **⑩ 팀별 가시성 분리** — 역할이 `viewer < analyst < remediator < admin` 한 축뿐이라
  Viewer 하나면 모든 연결·탐지 결과·계정을 본다. "결제팀은 결제팀만"이 불가능하다.
  사업부마다 따로 띄우면 지문 키가 갈려 사업부 간 같은 자격증명 대조가 안 된다.
  데이터 모델에 소유 축을 추가하는 일이라 규모가 다르다.
