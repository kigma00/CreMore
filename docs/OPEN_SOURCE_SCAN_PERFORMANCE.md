# 오픈소스 공개 준비 상태와 대규모 스캔 성능 설명

작성일: 2026-09-15. 대상: CreMore 운영 담당자, 보안팀, 도입 검토자.

## 1. 지금 오픈소스로 배포할 수 있는가?

**소스 공개·설치·평가를 위한 구현과 로컬 검증은 준비됐다. 다만 정식 릴리스 검증과 실제 기업 환경의 운영·성능 검증까지 완료된 상태는 아니다.** 현재 상태는 공개 후보로 설명하는 것이 정확하다. 이 문서는 코드 공개나 이미지 게시를 실행한 기록이 아니다.

| 구분 | 확인한 상태 |
| --- | --- |
| 기능·사용법 | 선택·증분 스캔, 작업 복구, 플랫폼별 가속, 이벤트 연동 구현. [README](../README.md)에 설치·연결·실행 예제 제공 |
| 성능 | 수정 뒤 최초 스캔 시간 감소: S3 43.40%, GitHub 47.80%, Notion 33.70%. 각 1만 항목·3회 중앙값이며 재스캔도 감소. 4.6절의 로컬 합성 데이터 결과로 실제 클라우드 성능 보장이 아님 |
| 기능 검증 | 이전 구현 전체 검증: Python 3,211개, 별도 PostgreSQL DB/재점수 129개, 웹 353개, Helm/Compose 41개 통과. 이번 성능 수정: 수집·스캔 관련 288개 통과·PostgreSQL 전용 8개 생략, 추가 엔진 수정 후 탐지·서비스 캐시 2,717개 통과. 범위가 중복되며 전체 릴리스 검증을 다시 수행했다는 뜻이 아님 |

공개 직전에 다음은 확인해야 한다.

- **게시할 정확한 커밋의 CI·Security 통과:** 현재 [release workflow](../.github/workflows/release.yml)는 `v*` 태그로 독립 실행되어, CI/Security 성공을 자동으로 기다리지 않는다. 검사된 커밋만 태그·게시하도록 보호된 승인 절차가 필요하다. 서명/SBOM/provenance 생성 코드가 있다는 것과 이 검증이 연결되어 있다는 것은 다르다.
- **공개할 Git 이력과 산출물:** 현재 저장소 비밀정보 회귀 테스트는 추적 파일과 무시되지 않은 신규 파일을 검사한다. 전체 과거 커밋·배포 이미지에 비밀정보가 없음을 증명하지 않는다. 최종 CodeQL·이미지 검사·게시된 서명 검증, 저장소/패키지 공개 설정과 비공개 취약점 신고 채널을 확인한다.
- **운영 승인은 별도:** 조직의 IAM/OIDC/Vault, 자격증명 갱신, 전용 SQS, Inventory, 실제 소스 연결, 운영 DB 업그레이드·복구와 대규모 부하를 확인한다. Kubernetes는 필수가 아니지만 조직별 신원·권한·DB 설정은 필요하다. 다른 기업의 설정을 자동으로 덮어쓰지 않는다.

기존 전체 테스트의 명령과 범위는 [구현·운영 기록](SCANNING_IMPLEMENTATION.md#검증-기록)에 있다. 현재 저장소 전체 확장 Ruff에는 기존 진단 171개가 남아 있어 전체 lint까지 모두 통과했다고 표현하지 않는다. 변경 줄·신규 Python 파일 진단과 핵심 오류 검사는 별도로 확인했다.

## 2. 담당자에게 쉽게 설명하기

> 기존에는 검사할 때마다 파일을 내려받고 내용을 다시 검사했습니다. 이제는 먼저 담당자가 승인한 범위를 정하고, 최초 검사 이후에는 수정 시각이나 내용 식별값을 확인해서 바뀐 내용과 재검사가 필요한 대상을 중심으로 읽습니다. GitHub는 최초 전체 저장소 검사에서 파일마다 요청하는 대신 묶음 다운로드를 사용합니다. S3는 수정된 객체와 이전 실패 객체를 우선 읽고, Notion은 페이지별 수정 여부를 확인해 바뀌지 않은 페이지 본문을 생략합니다. 작업을 작은 단위로 나누고 중단 지점을 저장해서 장애 때문에 처음부터 다시 하는 일도 줄였습니다. 단, 확인하지 않은 대상을 안전하다고 처리하거나 파일에서 키가 사라졌다는 이유만으로 위험이 해결됐다고 표시하지는 않습니다.

핵심은 **검사를 대충 하는 것이 아니라, 반복 다운로드·반복 탐지·장애 후 반복 작업을 줄이는 것**이다. 최초 스캔과 재스캔의 효과는 다르다. 최초에 반드시 읽어야 할 새로운 내용까지 없어지는 것은 아니다.

최초 스캔 지연도 별도로 수정했다. 작은 GitHub 파일을 읽을 때 최대 허용 크기의 버퍼를 요청하던 부분을 실제 파일 크기에 맞췄고, 객체마다 반복하던 시각 변환·같은 대상 식별값 계산·동일 저장소 복사를 줄였다. 탐지엔진에서는 같은 본문에 같은 규칙의 키워드를 두 번 찾던 작업을 한 번으로 합쳤다. 파일 크기 제한·본문 마스킹·승인 범위·변경 여부 확인은 유지했다.

## 3. 최초 스캔과 재스캔에서 적용한 방법

| 대상 | 최초 스캔 | 재스캔 | 여전히 필요한 일 |
| --- | --- | --- | --- |
| 공통 | 승인한 bucket/prefix/repository/page만 선택. 서로 다른 root 작업을 여러 worker로 처리 | 변경·실패 대상을 우선 처리. 완료 지점과 작업 소유권을 저장해 안전하게 재개 | 선택 범위를 줄인 것은 동일 범위 성능 개선과 구분. 같은 대상은 충돌 방지를 위해 직렬화 |
| S3 | 최초 기준이 없으면 승인 범위의 내용을 읽음. 같은 범위·같은 worker라면 다운로드 수 감소를 보장하지 않음 | 수정 시각과 기준 시각을 비교하고 겹침 구간·실패 키를 함께 재검사. 일반 목록에서 ETag·크기·LastModified 사용 | 일반 DELTA도 전체 승인 범위의 목록 조회는 필요. 기준·규칙 변경이나 실패 목록 초과 시 더 넓게 다시 검사 |
| GitHub | 전체 저장소 읽기가 승인된 경우 commit SHA에 고정한 tarball로 묶음 다운로드. tree와 blob hash로 누락·내용 변경 검증 후 필요한 blob 보충 | blob SHA가 같으면 마스킹된 탐지 결과를 재사용. 빈 결과도 캐시. 이름이 바뀌면 새 경로의 규칙·위험도를 다시 적용 | tree 확인, 새 SHA의 내용 검사. 캐시 만료·규칙 변경 시 재검사. 경로 제한 스캔은 전체 tarball을 받지 않음 |
| Notion | 부모 본문과 별도 하위 페이지를 분리하여 승인하지 않은 하위 페이지까지 읽지 않음 | 페이지 수정 시각을 확인하고 변경된 페이지의 본문만 읽음 | 페이지 metadata 조회. 완독 중 변경이 없었는지 header 재확인(2026-10-10에 없앰, 아래 Notion 절 갱신 메모). 검색 누락·404는 삭제 증거가 아님 |
| Inventory·이벤트 | 이미 존재하는 Inventory 보고서나 승인된 전용 이벤트 경로를 선택적으로 사용 | 보고서 비교나 변경 알림으로 우선 검사할 대상을 좁힘. 반복 알림은 대기 작업에서 합침 | Inventory는 지연·필터된 보고서 범위에 한정. 이벤트만 믿지 않고 주기적으로 대조. 기존 공유 큐는 소비하지 않음 |

추가로 DB에서는 노출 중복 방지·원자적 upsert와 필요한 개수/대표 조회를 사용해 매 탐지마다 전체 노출 목록을 반복해서 불러오지 않도록 했다. 이번 아래 벤치마크는 탐지가 없는 합성 데이터이므로 **탐지가 많은 DB 저장 경로의 개선 배수는 측정하지 않았다.**

## 4. 수치의 해석 원칙

4.1~4.5절은 성능 수정 전 측정·원인 조사 기록을 보존한 것이다. 이후 적용한 수정과 재검증 결과는 4.6절에 구분해서 기록한다. 이전 원시 표본을 새 코드의 측정값으로 바꾸어 쓰지 않는다.

수치는 두 종류로 구분한다.

1. **로컬 코드 실측:** 같은 합성 데이터를 실제 기존/개선 수집·검사 코드로 실행한 시간. 실제 AWS·GitHub·Notion 서버와 통신하지 않는다.
2. **가정 계산:** 객체 수와 요청당 소요 시간을 정해 계산한 예시. 실제 제품 처리시간이나 고객 환경 성능 보장이 아니다.

기존 기준은 `8780f9d31191090d35e81f86df8394e4c002da10`이며, 개선 기준은 측정 시점의 작업트리다. S3는 각 버전의 Python 모듈을 별도 프로세스에 로드하고 같은 builtin 탐지 catalog·설정으로 수집기와 검사 서비스를 실행한다. GitHub/Notion의 4.2~4.5절 과거 측정은 각 버전의 수집기·검사 서비스·HTTP helper에 공통 당시 Engine·Orchestrator·메모리 저장소를 사용한다. 4.6절에서는 엔진 최적화까지 포함하기 위해 `--versioned-engine`으로 각 버전의 Engine을 비교하며, catalog·탐지 helper·EngineConfig·Orchestrator·메모리 저장소·domain model은 여전히 공유한다. 합성 provider와 메모리 DB를 사용하므로 실제 네트워크 지연·TLS·PostgreSQL·worker 큐·병렬화 효과는 측정하지 않는다. 이전 릴리스 전체와 신규 릴리스 전체를 운영 배포해 비교한 결과가 아니며, 서로 다른 비교 범위의 배수를 평균 내어 전체 프로젝트 개선율로 제시하지 않는다.

비교 장비는 Windows, Intel Core Ultra 7 255H, 논리 프로세서 16개, 메모리 약 15.43 GiB, Python 3.12.9다. 실서비스 지연을 흉내 내기 위한 인위적인 sleep은 넣지 않는다. 데이터 준비와 캐시 준비 위치, 실제 실행 범위·표본 수·요청 수는 재현 스크립트의 결과와 함께 기록한다. 서비스가 실제로 사용하는 안전 검사 비용도 측정에 포함한다.

### 4.1 S3 — 실제 코드의 로컬 측정

조건: 객체 **10,000개 × 4KiB = 39.06MiB**, 한 prefix, 새 상태에서 최초 검사 후 **100개(1%)** 수정, 조건당 **3회 중앙값**. 아래는 실행 순서를 기존→개선 / 개선→기존 / 기존→개선으로 교대한 재확인 결과다. 양쪽 탐지 0건·실패 0건인 비밀 없는 문서다. 원본 LIST/GET은 메모리의 합성 S3 응답이며 실제 AWS 요청은 0회다.

| 검사 | 기존 | 개선 경로 | 이번 로컬 측정 결과 |
| --- | ---: | ---: | --- |
| 최초, 동일한 1만 객체 | 17.422초 / 0.290분 | 17.871초 / 0.298분 | 중앙값 **2.58% 증가**; 최초 시간 개선을 확인하지 못함 |
| 재스캔, 1% 변경 | 17.545초 / 0.292분 | 0.194초 / 0.00324분 | **98.89% 감소, 약 90.28배** |

| 처리량 | 기존 최초 | 개선 최초 | 기존 재스캔 | 개선 재스캔 |
| --- | ---: | ---: | ---: | ---: |
| LIST 호출 | 10 | 10 | 10 | 10 |
| GET / 탐지엔진 실행 | 10,000 / 10,000 | 10,000 / 10,000 | 10,000 / 10,000 | 100 / 100 |
| 읽은 본문 | 39.06MiB | 39.06MiB | 39.06MiB | 0.391MiB |
| 변경 없음으로 건너뛴 객체 | 0 | 0 | 0 | 9,900 |

버킷 공개 차단 설정의 metadata 조회는 각 실행에서 별도로 1회씩이다. 재스캔에서도 1만 객체 목록은 확인하고 100개 본문만 읽었다. 따라서 "목록도 99% 줄었다"거나 "1만 개를 다시 완독했다"는 뜻이 아니다.

첫 검사는 양쪽 GET·탐지 횟수가 같다. 새 경로의 캐시 조회·계측·객체 단위 reconciliation 등을 포함한 전체 서비스 비용이 측정됐지만, 개별 비용의 인과관계를 분리한 profiler 실험은 아니다. **이 측정 시점에는 동일 범위 S3 최초 스캔의 추가 최적화가 필요했다. 수정 뒤 결과는 4.6절에 있다.** 재스캔의 주요 절감은 본문 읽기와 탐지 실행을 10,000회에서 100회로 줄인 것이다.

변동 범위: 최초 기존 17.212~17.962초 / 개선 17.637~18.412초, 재스캔 기존 17.286~17.795초 / 개선 0.193~0.221초. 각 기존/개선 표본은 별도 프로세스에서 최초·재스캔 한 쌍을 수행하며, 다른 플랫폼 벤치마크와는 동시에 실행하지 않았다. 일반 개발 장비의 CPU 발열·OS 부하를 완전히 통제한 실험은 아니고, 3회 표본의 중앙값이지 운영 SLA나 p95가 아니다.

재현: 기준 커밋을 포함한 Git checkout과 프로젝트 Python 의존성이 필요하다. 제품 DB나 `.env`는 사용하지 않으며 스크립트는 네트워크 접근을 차단한다. 초기 엔진 생성·데이터 생성·collector 구성·변경 데이터 준비는 타이머 밖이고, `ScanService.run`을 측정한다. 매 반복은 새 메모리 저장소에서 시작하며 재스캔에는 해당 최초 검사의 상태를 유지한다. watermark는 수집기에 직접 전달하므로 durable worker의 체크포인트·lease 저장 비용은 제외된다.

```bash
python -m scripts.benchmark_s3_scan --objects 10000 --object-bytes 4096 --change-rate 0.01 --repeats 3
```

[재현 스크립트](../scripts/benchmark_s3_scan.py) · [교대 실행 원시 JSON: 모든 표본·데이터/실행 모듈 hash](benchmarks/s3-paired-synthetic-2026-09-15.json). 두 버전의 데이터 hash와 builtin catalog hash가 같고, 최초 측정 때와 각 제품 버전의 실행 모듈 hash가 그대로임을 확인했다.

**측정 정정 기록:** 먼저 기존 표본을 모두 실행한 뒤 개선 표본을 실행했던 첫 측정에서는 최초 24.822→35.269초(+42.09%), 재스캔 23.599→0.494초였다. 그 [원시 결과도 삭제하지 않고 보존](benchmarks/s3-synthetic-2026-09-15.json)했다. 최초 지연 문제 제기에 따라 프로파일과 사전에 정한 교대 실행 3회 비교를 한 번 더 수행했다. **제품 최적화로 42% 회귀를 고친 것이 아니며, 처음의 42%를 코드 변경 자체의 고정 회귀율로 단정할 수 없다.** 재스캔 이점은 두 실험에서 모두 보이지만 정확한 배수는 장비·측정 조건에 의존한다. 유리한 결과가 나올 때까지 반복하거나 불리한 표본을 제거하지 않았다.

### 4.2 GitHub — 실제 코드의 로컬 측정

조건: 전체 저장소 읽기를 승인한 파일 **10,000개 × 4KiB**, 서로 다른 blob SHA, 이후 **100개 변경**, 각 **3회 중앙값**. 기존/개선 실행 순서를 반복마다 교대했다. 최초는 빈 캐시로 시작하고, 측정한 최초 검사가 저장한 결과를 재스캔에 사용했다. 숨겨진 사전 캐시 채우기나 기존 기능의 강제 비활성화는 없다.

| 검사 | 기존 | 개선 경로 | 이번 로컬 측정 결과 |
| --- | ---: | ---: | --- |
| 최초 | 21.316초 / 0.355분 | 25.970초 / 0.433분 | 중앙값 **21.83% 증가**; 시간 개선을 확인하지 못함 |

| 처리량 | 기존 최초 | 개선 최초 | 기존 재스캔 | 개선 재스캔 |
| --- | ---: | ---: | ---: | ---: |
| HTTP 요청 | 10,002 | 5 | 10,002 | 103 |
| 파일별 blob 요청 | 10,000 | 0 | 10,000 | 100 |

최초의 5회는 저장소 metadata·commit·tree·archive redirect·archive 본문이다. fallback blob 호출 없이 archive를 끝까지 처리했다. 최초에도 새 파일 1만 개의 탐지는 필요하고 압축 해제·blob hash 검증·캐시 작성 비용이 생기므로, **네트워크 왕복을 제외한 이번 실험에서는 요청 감소가 곧 시간 단축으로 이어지지 않았다.** 실제 GitHub에서 왕복 지연·호출 제한을 줄이는 효과는 별도의 클라우드 실측 대상이다.

최초 표본 범위는 기존 20.875~29.021초 / 개선 25.825~29.411초, 재스캔은 기존 20.828~22.535초 / 개선 0.355~0.394초다. 3회 중앙값의 차이를 통계적으로 확정된 모든 환경의 고정 회귀율로 해석하지 않는다.

데이터는 매우 반복적인 합성 문장이다. 이 실험의 gzip archive는 약 236KiB이며 JSON 응답의 HTTP Content-Encoding 압축은 모사하지 않았다. **JSON에 있는 응답 byte 감소율을 실제 GitHub 전송량·요금 절감률로 인용하지 않는다.** 서버에서 archive를 생성하는 지연 역시 측정하지 않았다.

### 4.3 Notion — 실제 코드의 로컬 측정

조건: 명시적으로 승인한 **10,000개 독립 페이지 × 본문 4KiB**, 페이지당 본문 블록 응답 한 번, 이후 **100개 변경**, 각 **3회 중앙값**. 하위 페이지가 없는 동일한 평면 구성을 사용해 승인 범위 축소나 부모·자식 중복 제거를 속도 개선에 섞지 않았다.

### 4.4 최초 스캔이 느려진 것은 문제인가?

그렇다. **같은 승인 범위의 최초 스캔 지연은 재스캔 성과로 덮을 문제가 아니다.** 다만 S3 첫 측정의 42%는 교대 실행에서 재현되지 않았고 중앙값 차이가 2.58%였으므로, 42% 전체를 코드 자체의 고정 회귀율로 단정한 설명은 정정한다. 작은 차이도 최초 스캔 개선 성과로 바꿔 말하지 않는다.

추가로 S3 객체 1,000개·4KiB를 6번씩 전부 읽는 조건에서 `ScanService.run`에만 Python `cProfile`을 적용했다. 프로파일러 자체의 비용이 있으므로 다음은 성능 표의 대체값이 아니라 비용 분해용 결과다.

| 프로파일 누적 구간 | 기존 | 개선 |
| --- | ---: | ---: |
| 검사 서비스 전체 | 16.275초 | 16.703초 |
| 그중 탐지엔진 | 16.058초 | 15.628초 |
| 서비스 전체에서 탐지엔진을 뺀 구간 | 0.217초 | 1.074초 |

새 경로에서 6,000객체당 revision 생성 12,000회, root/cache-key digest 12,000회, 캐시 조회·orchestrator 바인딩·객체 대조 각각 6,000회가 추가되는 것을 확인했다. 이 부가 비용은 실제 존재한다. 하지만 이 프로파일의 서비스 전체 차이는 약 2.6%이고 원래 1만 객체 실험의 차이 전체를 설명하지 못해 위의 교대 실행을 추가했다. 특정 환경 요인이 첫 42% 차이 중 몇 %를 만들었는지까지는 확정하지 않았다. 기존에도 있던 정규식·마스킹을 새 회귀 원인으로 지목하지 않으며, 이 벤치마크에 없는 SQL·lease 비용 탓으로 돌리지 않는다.

[비용 분해 원시 결과](benchmarks/s3-profile-2026-09-15.json). 제품 코드를 고치지 않고 측정한 결과이며, 안전 검사를 끄거나 최초 검사 대상을 줄여 성능 수치를 맞추지 않았다.

### 4.5 최초 스캔 지연의 원인 조사 — 추가 확인

**결론: 최초 검사에서는 변경분 생략의 이득이 없는데, 재스캔용 캐시 준비와 정합성 확인 비용이 추가됐다. 여기에 GitHub archive가 작은 파일에도 지나치게 큰 읽기 크기를 요청하는 구체적인 비효율이 확인됐다.** 아래는 수정 전 원인 조사 기록이며, 이후 수정은 4.6절에 기록한다.

#### GitHub: 작은 파일에도 50MiB 읽기 크기를 요청

[archive 읽기](../cremore/collectors/github_archive.py)의 `stream.read(max_object_bytes + 1)`은 파일의 실제 크기가 아니라 허용 상한을 사용한다. 수집기·Python 설정·Helm의 기본 상한은 모두 50MiB다. `extractfile()`이 반환하는 객체는 `io.BufferedReader`이므로, 그 아래의 tar 멤버 리더가 실제 파일 길이로 제한해도 바깥의 버퍼 할당 비용까지 없어지지는 않는다. 다른 파일까지 읽었다거나 네트워크로 파일당 50MiB를 내려받았다는 뜻은 아니다.

이를 분리하기 위해 **동일한 1,000개 × 4KiB 파일**을 같은 실제 archive 수집기로 읽되, 객체 허용 상한만 기본값과 4KiB로 바꿔 비교했다. 세 번 교대 실행하고, 메모리는 각 조건에서 별도 한 번 `tracemalloc`으로 측정했다. 데이터 생성·압축은 타이머 밖이고 탐지엔진·DB는 실행하지 않았다. 측정에는 client·collector 구성, metadata·tree 요청/파싱, archive 읽기, 반환 결과 hash·assertion과 정리가 포함된다. 순수 압축 해제 함수만의 시간이 아니다.

| archive 수집 경로, 탐지·DB 제외 | 기본 50MiB 상한 | 실제 파일과 같은 4KiB 상한 |
| --- | ---: | ---: |
| 시간 중앙값 | 0.403초 | 0.031초 |
| 시간 표본 범위 | 0.402~0.462초 | 0.027~0.036초 |
| 별도 측정 Python 추적 메모리 피크 | 51.19MiB | 1.20MiB |
| 반환 파일·본문 합계 | 1,000개 / 4,096,000 bytes | 동일 |
| HTTP 요청 / archive / blob 보충 | 5 / 1 / 0 | 동일 |

반환 내용 전체의 SHA256, 파일 수·크기, 개별 Git blob hash 검증, 실패 0건이 양쪽에서 같았다. **같은 파일을 읽는데 요청 크기만으로 시간과 임시 메모리가 크게 바뀌므로, 과도한 버퍼 할당·반환은 실측으로 뒷받침되는 원인이다.** 메모리 수치는 전체 프로세스 RSS나 유지되는 캐시 크기가 아니라 이 읽기 경로의 Python 추적 피크다.

해결 방향은 **운영자의 50MiB 허용 범위는 유지하면서 이미 검증한 `member.size`에 맞춰 읽는 것**이다. 운영 설정을 4KiB로 낮춰 큰 파일을 검사에서 제외하자는 뜻이 아니다. 기존 최대 크기·실제 길이·SHA 검증과 archive 전체 제한은 유지해야 한다. 이 분리 실험의 약 13배는 archive 수집 경로만의 차이이며, 전체 스캔이 13배 빨라진다는 뜻도, 이전 1만 파일 측정의 추가 4.654초 전부를 설명했다는 뜻도 아니다.

[읽기 크기 실험 원시 결과](benchmarks/github-archive-read-probe-2026-09-15.json).

#### S3: 객체별 반복 계산과 캐시 확인

앞 절의 기존 S3 프로파일에서는 6,000개 처리 기준 엔진 바깥의 시간이 0.217초에서 1.074초로 늘었다. [수집기](../cremore/collectors/s3.py)는 LIST와 GET의 revision을 각각 만들고, 각 관측 안에서도 같은 수정 시각을 revision과 metadata용으로 다시 문자열화한다. [검사 서비스](../cremore/scanning/service.py)는 같은 bucket의 root hash를 객체마다 계산하고, 최초 캐시 miss에서도 조회 키를 만든다. [orchestrator 바인딩](../cremore/scanning/orchestrator.py)은 같은 저장소를 쓸 때도 객체마다 복사한다.

- 줄일 후보: 동일 root hash 재사용, 한 관측 안의 시간값 정규화 재사용, 동일 저장소를 사용하는 경우의 불필요한 복사.
- 유지할 것: LIST 이후 GET에서 내용이 바뀌었는지 확인하는 revision 갱신, 실제 worker의 lease 소유권 검증, 객체별 쓰기 정합성.
- 주원인으로 지목할 수 없는 것: S3의 빈 탐지 결과 저장은 하지 않는다. 기존 프로파일에서 빈 `cache()` 호출은 6,000회 합계 0.0017초, 객체 reconcile은 0.0301초였다. 이 메모리 실험을 SQL 병목으로 설명하면 안 된다.

#### Notion: 페이지당 정합성 확인 요청 한 번 추가

> 갱신(2026-10-10): 본문 뒤 header 재확인은 `4d54ce14`에서 없앴다. 실행의 기준선(watermark)이 그 실행의 시작 시각이고,
> 다음 증분 실행은 기준선에서 겹침만큼 앞선 시각 이후에 수정된 모든 페이지를 읽으므로 본문을 읽는 동안 생긴 수정도 다음
> 실행이 읽는다. Notion 수정 시각은 분 단위라 재확인은 같은 분 안의 수정을 잡지 못했다. 탐지가 있는 페이지만은 위치를 보강하는
> 블록 조회 뒤 머리글을 한 번 더 읽어 본문과 같은 revision인지와 지금의 주소·제목을 확인한다. 이 문서의 Notion 요청 수(최초
> 3만 회 등)는 당시 측정이다. 지금의 요청 수는 [스캔 속도 설계와 측정](SCAN_PERFORMANCE_2026-10-09.md) 5절에 있다.

[Notion 수집기](../cremore/collectors/notion.py)는 본문 완독 뒤 페이지 header를 다시 확인한다. 읽는 도중 내용이 바뀐 페이지를 같은 revision의 완전한 결과로 저장하지 않기 위한 장치다. 독립 페이지 1만 개의 최초 검사는 따라서 **2만 요청에서 3만 요청으로 증가**한다. 이는 불필요한 재다운로드가 아니라 새 정합성 보장의 비용이다. 다만 실제 공급자 호출 제한에서 부담이 커질 수 있으므로 최초 지연을 무시해도 된다는 뜻은 아니다.

본문 재확인을 제거하는 대신, 캐시를 사용하지 않는 Notion에서도 계산하는 root digest 등 불필요한 공통 처리를 먼저 줄여야 한다. 동시성을 늘려도 공급자 전체 요청 제한을 없앨 수 없으며, 이번에는 병렬화 효과를 측정하지 않았다.

### 4.6 최초 스캔 성능 수정 결과

적용한 수정:

- **GitHub:** 검증한 `member.size`만큼만 archive 멤버를 읽는다. 파일 허용 상한 50MiB는 유지한다. 길이·Git blob SHA·archive 전체 크기/시간·리다이렉트 검증, 누락/변형 파일의 blob 보충은 그대로다.
- **S3:** LIST와 GET에서 각각 한 번만 수정 시각을 정규화하고 revision·metadata·워터마크 비교에 재사용한다. GET에서 내용이 바뀌면 revision·크기·ETag·VersionId를 여전히 새 값으로 갱신한다. Inventory의 기존 revision 생성 계약도 유지한다.
- **공통:** 한 번의 스캔 안에서 바로 앞 root의 식별값 하나만 재사용한다. root·소스·연결이 바뀌면 재계산하며, 객체별 상태를 무제한 저장하지 않는다. 캐시를 사용하지 않는 Notion에는 이 hash를 만들지 않는다.
- **저장소 바인딩:** 동일한 저장소에는 orchestrator와 ScanStore를 재사용한다. 다른 lease-fenced 저장소에는 별도 바인딩을 유지하므로 이전 작업 소유자가 쓰거나 다른 연결의 캐시를 재사용하도록 바뀌지 않는다.
- **탐지엔진:** 본문별로 키워드가 맞는 규칙을 순서대로 한 번 선택하고, 마스킹과 탐지에서 그 목록을 공유한다. 실제 패턴 검사 두 경로와 출력 상한 이전의 전체 후보 마스킹은 유지한다. 디코딩된 내용은 각각 다시 선택한다. 탐지 의미가 바뀌지 않아 기존 detection digest도 그대로다.

Notion의 본문 후 header 확인은 유지했다. 이 요청을 제거해 최초 처리시간을 줄이면 읽는 중 변경된 페이지를 완전한 revision으로 잘못 확정할 수 있다. 공급자 검증 활성화 설정·보안 정책·검사 범위·프로젝트 의존성은 변경하지 않았다. (갱신 2026-10-10: 이 확인은 이후 없앴다. 이유는 위 "Notion: 페이지당 정합성 확인 요청 한 번 추가"의 갱신 메모에 있다.)

회귀 검증:

- GitHub 수정 전 빈 파일·4KiB·1MiB 멤버의 읽기 크기 테스트 3개가 실패했고, 수정 후 모두 통과했다. 설정 상한, 짧은 읽기의 fallback, 기존 archive 보호 장치를 포함해 관련 27개 테스트가 통과했다.
- S3 수정 전 LIST의 동일 시각 정규화는 객체당 3번, GET은 2번이었다. 현재 각 관측당 한 번이며, LIST 후 GET에서 내용이 바뀌는 경우도 확인했다.
- 공통 수정 전 root hash 반복·동일 저장소 복사 테스트 4개가 실패했고 수정 후 통과했다. 서로 다른 저장소에 노출과 캐시를 쓰는 경계도 유지됐다.
- 수집·스캔·worker·DB 관련 통합 범위 **288개 통과, PostgreSQL 전용 8개 생략**. 이번 수정 후 실제 PostgreSQL 통합 검증은 수행하지 않았다. 이전 별도 PostgreSQL 검증 결과와 혼동하지 않는다.
- 변경된 검사 서비스·신규 테스트·archive 코드와 스크립트 Ruff, 핵심 Python 오류 검사가 통과했다. S3 기존 예외 처리의 전체 스타일 진단은 이 성능 수정 범위 밖이다.
- 엔진 추가 수정 후 탐지 전체·서비스 캐시 테스트 **2,717개 통과**. 키워드 없는 규칙·여러 키워드·대소문자·출력 순서·상한 이후 후보 마스킹·FP로 출력이 억제된 후보의 마스킹·디코더 우선순위를 확인했다. 위 288개와 일부 중복되므로 두 숫자를 더해 총 테스트 수로 표시하지 않는다.

수정 과정의 중간 측정도 보존한다. archive·S3·공통 경로만 고친 뒤 S3 1만 객체를 교대 비교했을 때 최초 **41.829초 → 43.824초**로 약 4.77% 느렸다. [중간 원시 결과](benchmarks/s3-fixed-synthetic-2026-09-15.json)를 삭제하지 않았다. 이 결과로 최초 스캔 개선을 선언하지 않고, 기존에도 있었지만 비용이 컸던 엔진의 중복 키워드 검사를 추가로 줄였다. 그때 진행 중이던 GitHub·Notion 실행은 완료 전에 중단했으며 완성된 측정값이 없으므로 최종 결과에 포함하지 않았다.

S3 최초 GET와 탐지 횟수는 양쪽 모두 10,000회다. 재스캔은 본문 GET·탐지 10,000회 → 100회이고, LIST는 양쪽 모두 10회로 같다. 즉, 최초 개선은 검사량을 줄여서 얻은 값이 아니고 재스캔은 변경되지 않은 본문 9,900개의 반복 읽기·탐지를 생략한 결과다. 버킷 metadata 조회는 실행당 별도로 1회다.

GitHub 최초 HTTP 요청은 **10,002회 → 5회**, 재스캔은 **10,002회 → 103회**다. 최초 양쪽 모두 1만 본문·39.06MiB를 탐지했고, 재스캔은 100개만 다시 탐지하고 9,900개 결과를 캐시에서 재사용했다. 전체 저장소 승인을 전제로 하며, 누락 blob 보충이 없는 fixture다. 서버 archive 생성 지연·실제 압축률·API 제한을 모사하지 않아 요청 감소율을 클라우드 시간 감소율로 바꾸어 말하지 않는다.

Notion은 명시적으로 승인한 하위 페이지 없는 독립 페이지 1만 개다. 최초 HTTP 요청은 정합성 확인 때문에 **20,000회 → 30,000회**로 늘었지만 이번 네트워크 없는 측정에서는 CPU·공통 처리 절감으로 전체 시간이 줄었다. **실제 Notion의 요청 제한 환경에서 최초 스캔이 빨라졌다는 증거는 아니다.** 재스캔 요청은 **20,000회 → 10,200회**, 본문 다운로드·탐지는 10,000개 → 100개이며 9,900개는 header 확인 뒤 생략했다. 첫 스캔 양쪽 본문량은 39.06MiB로 같다.

[S3 최종 원시 결과](benchmarks/s3-optimized-synthetic-2026-09-15.json) · [GitHub·Notion 최종 원시 결과](benchmarks/github-notion-optimized-synthetic-2026-09-15.json). 이전 결과와 시간이 달라진 것을 모두 코드 효과로 해석하지 않는다. 절감률은 **이번 실행 안의 기존/수정 쌍**으로 계산하며, 과거 17.422초와 이번 23.772초처럼 다른 세션의 값끼리 비교하지 않는다. GitHub 기존 최초 표본 중 48.029초도 제거하지 않고 포함했다. 그 지연 원인은 확정하지 않았으며 모든 표본·중앙값·범위를 공개한다.

표의 값은 일반 개발 장비의 3회 중앙값으로, p95·SLA·실제 클라우드 처리시간은 아니다. 무탐지 합성 문장이므로 모든 규칙이 매칭되는 파일이나 finding이 많은 DB 저장 경로로 일반화하지 않는다. 최초 감소율은 이번 수정까지 적용한 코드와 고정 기준 코드의 차이이며, archive·엔진·공통 처리 각각의 기여도를 이 표에서 분리 산출하지 않는다. GitHub·Notion 최종 비교에는 버전별 Engine을 사용했지만 Orchestrator·메모리 저장소 등은 공통이므로 전체 릴리스 개선율로 표현하지 않는다. 현재 스크립트를 다시 실행하면 현재 코드가 측정되며, 과거 결과를 재현하려면 해당 JSON의 소스 hash와 같은 당시 코드가 필요하다.


## 5. 10만 객체라면 몇 분인가? — 실측이 아닌 계산 예시

아래는 **S3 일반 목록 + 본문 GET에 걸리는 시간만** 단순 계산한 것이다. 실제 클라우드에서 10만 객체를 검사한 결과로 인용하면 안 된다.

가정:

- 한 bucket의 승인 prefix에 객체 100,000개, 목록 한 번에 1,000개 반환 → 목록 100회.
- 최초에는 전부 새로운 내용, 재스캔에는 겹침 구간까지 포함한 검사 후보가 1,000개(1%). 실패 재시도·정책 변경·권한 오류 없음.
- worker 하나가 순차 처리. LIST/GET 한 번의 평균 시간은 모두 **가정값 50ms**.
- 객체 다운로드 시간도 위 가정 안에 포함한다고 단순화. 실제 파일 크기·대역폭은 별도로 측정해야 함.
- 탐지 CPU, DB, queue 대기, 재시도, 자격증명 갱신, Inventory 생성 대기와 주기적 전체 대조 비용은 제외.

`요청 시간(분) = (LIST 횟수 + GET 횟수) × 0.05초 ÷ 60`

| 검사 | 기존 요청 | 개선 후 요청 | 기존 요청 시간 | 개선 후 요청 시간 | 이 모델의 감소율 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 최초, 동일한 10만 객체 | 100 + 100,000 | 100 + 100,000 | 83.42분 | 83.42분 | 0% |
| 재스캔, 검사 후보 1% | 100 + 100,000 | 100 + 1,000 | 83.42분 | 0.92분 | 98.90% |

이 예시는 왜 재스캔에 효과가 큰지 설명하기 위한 것이다. **"실제 83분이 55초로 줄었다"는 실측 주장은 할 수 없다.** 변경률이 높거나 목록 조회·DB·큰 파일의 검사 시간이 지배적이면 효과는 작아진다. 정기 전체 대조를 포함한 하루/일주일 총 운영 비용도 별도로 계산해야 한다.

## 6. 개조식 설명 — 회의·메일용

- 목적: 승인 범위의 검사 정확성을 유지하면서 반복 다운로드·반복 탐지·장애 후 재작업 최소화.
- 최초 스캔:
  - 검사할 bucket/prefix/repository/page를 명시적으로 선택.
  - GitHub 전체 저장소는 SHA 검증 tarball로 파일별 다운로드 요청 축소.
  - Notion 부모·하위 페이지의 승인 경계를 분리하여 중복 수집 방지.
  - 작업을 root 단위로 나누어 서로 다른 대상을 병렬 처리.
  - 실제 파일 크기에 맞춰 archive 읽기; 같은 root·시각·저장소 바인딩의 반복 처리 감소.
  - 탐지 규칙의 본문 키워드 판별은 한 번 수행해 마스킹·탐지에서 공유; 검사 범위와 마스킹 유지.
  - S3의 동일 범위 최초 본문 다운로드는 원칙적으로 필요; 일괄적인 최초 스캔 단축률을 주장하지 않음.
- 재스캔:
  - S3: 수정 시각 + 겹침 구간 + 이전 실패 키로 본문 읽기 대상 축소.
  - GitHub: blob SHA별 결과 캐시로 동일 내용의 다운로드·탐지 재실행 생략.
  - Notion: 페이지 수정 여부 확인 후 변경된 페이지 본문만 읽기.
  - Inventory 비교·전용 이벤트를 사용하면 변경 대상 발견을 보조하고 대기 이벤트를 병합.
- 안정성:
  - lease·checkpoint·멱등 저장으로 중단 작업 회수 및 안전한 재시도.
  - 변경된 탐지 규칙은 낮은 우선순위로 재검사; 이전 규칙의 완료 상태를 재사용하지 않음.
  - 실패·보관 티어·미지원·불완전한 목록은 안전 판정하지 않음.
  - 파일에서 키가 사라져도 키 폐기 확인 전까지 finding 자동 해결 금지.
  - 원본은 읽기 전용. 기업의 기존 알림·CloudTrail·Inventory·공유 큐를 덮어쓰거나 빼앗지 않음.
- 성과 표현:
  - 동일 범위 1만 항목 로컬 최초: S3 42.00→23.77초(43.40% 감소), GitHub 20.65→10.78초(47.80%), Notion 22.52→14.93초(33.70%).
  - 1% 변경 로컬 재스캔: S3 42.26→0.243초, GitHub 20.85→0.226초, Notion 22.32→1.285초. 3회 중앙값이며 클라우드 실측 아님.
  - 실제 측정 표에는 데이터 수·크기·변경률·측정 범위·전후 시간·요청 수를 함께 제시.
  - 로컬 코드 실측과 클라우드 시간 가정 계산을 분리.
  - worker 증설, Inventory, 이벤트, DB 최적화의 개별 시간 개선율은 별도 측정 전까지 미확정.

## 7. 고객 환경에서 최종 성능 수치를 확정하는 방법

1. 고객이 승인한 전용 시험 범위와 예산을 정한다. 같은 객체 수·크기 분포·규칙·권한·worker 수·DB 사양으로 비교하고, 운영 큐나 기존 provider 설정을 변경하지 않는다.
2. 최초 스캔은 새 시험 상태에서 실행한다. 양쪽 모두 완전한 동일 범위를 검사했는지 확인하고, 최초 완료 시간을 기록한다.
3. 같은 방식으로 1%·10%·100%를 변경하고 재스캔한다. 실패·삭제·이름 변경·Notion 하위 페이지·archive tier 사례도 별도로 검증한다.
4. 조건당 최소 3회 측정해 중앙값과 범위를 제시한다. API 요청 수, 내려받은 bytes, 실제 탐지 횟수, DB 시간, 실패/미검사와 비용을 함께 기록한다. 미검사로 빨라진 실행은 정상 완료와 비교하지 않는다.
5. `BASELINE`/`DELTA`뿐 아니라 주기적 `RECONCILE`, 규칙 변경 재스윕, worker 장애 복구와 캐시 만료도 포함해 하루 총 비용·완료 지연을 측정한다.
6. 그 결과가 있어야 "이 고객 환경에서 객체 N개 기준 최초 A분 → B분, 재스캔 C분 → D분"을 실측으로 제시한다. 지금은 그 외부 실험을 수행하지 않았다.

운영자 실행 예제와 예산·실패·migration·복구 절차는 [스캔 구현·운영 문서](SCANNING_IMPLEMENTATION.md)를 따른다.

## 8. 발견 키의 공급자 검증

**개발/운영 모드 구분은 제거됐다. 발견 키 검증은 운영 배포에서도 쓸 수 있는 핵심 기능이며, 원문 키를 외부로 보내므로 명시적으로 켜야 한다.**

| 기능 | 어떤 자격증명을 사용하는가? | 동작 조건 |
| --- | --- | --- |
| 연결 상태 점검 | 운영자가 연결에 등록한 자격증명·승인된 scanner 신원 | AWS/GitHub/Notion 지원. 별도 `credential-check` 경로로 항상 동작 |
| S3/GitHub/Notion 수집·스캔 | 운영자가 승인한 연결 신원으로 승인 범위를 읽음 | 항상 동작. 발견 키 검증 스위치와 별개 |
| 발견 키의 공급자 검증 | 읽은 콘텐츠에서 발견한 키를 발급 공급자에 보내 활성 여부와 비밀이 아닌 정보(계정, scope)를 확인 | 기본 켜짐. Admin이 대시보드 스위치로 끄고 켜며 다음 스캔부터 적용. `CREDENTIAL_VERIFICATION_MODE=disabled`면 설치 차원에서 잠김 |

코드 근거는 [Settings.validate_safety](../cremore/config.py), [Helm 검증](../deploy/helm/templates/validate.yaml), [검증기 등록](../cremore/detection/verify/__init__.py), [탐지엔진 검증 경계](../cremore/detection/engine.py)다.

- 검증 결과는 `verified`/`rejected`/`restricted`/`indeterminate`/`unsupported` 상태와 안전한 사실만 저장하고 원문 키는 저장하지 않는다.
- 탐지 패턴이 있다고 해서 해당 유형의 공급자 검증기가 있는 것은 아니다. 검증기가 없는 유형은 `unsupported`로 남는다.
- 검증은 수십 개 공급자에 HTTPS로 접속한다. egress 설계는 설치 조직의 선택이며, 공급자에 닿지 못한 결과는 `indeterminate`(`PROVIDER_UNREACHABLE`)로 기록된다.
- 콘텐츠 스캔 승인이 그 안의 모든 키를 사용할 권한을 증명하지는 않는다. 검증을 켤지는 설치 조직이 정책으로 결정한다.
