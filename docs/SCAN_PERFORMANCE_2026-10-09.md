# 스캔 속도·문서 형식·무인 스캔·병렬 처리·Slack 알림 설계와 측정

작성: 2026-10-10, 후속 작업 2026-10-11(13.1절). 기준 브랜치: `integration/saas-structure`(2026-10-09 요청부터 이 문서 커밋까지).

이 문서는 2026-10-09 요청의 모든 항목을 조사한 결과, 구현한 설계, 합성 측정과 검증을 정리한다. 측정은 모두
합성 데이터·가짜 공급자 클라이언트·격리된 일회용 PostgreSQL(`cremore_test`)·로컬 Linux 테스트 컨테이너에서
했다. 실제 고객 계정·실제 Slack 수신·운영 배포 성능은 검증하지 않았다(12절). IP 정보 보강은 처음에 보류했고, 2026-10-11에
이미 수집한 기록의 주소만 붙이는 범위로 넣었다(8.1절).

## 2. 시간이 어디에 쓰였나

요청 직후 코드를 끝까지 따라가며 확인한 병목이다.

- **탐지 엔진**: 내용마다 키워드 964개를 하나씩 `in`으로 찾아 돌릴 탐지기를 골랐다. 저장소 파일 600개(약 7MB)에서 이 고르기에만
  약 4.2초(MB당 약 0.57초)가 들었다(`scripts/bench_engine_routing.py`의 `plain`).
- **문서 추출**: PDF·DOCX 등 텍스트가 아닌 문서마다 `python -B -E -s worker.py`를 새로 띄웠다. 작은 DOCX도 문서당 약 0.37초가
  들었다.
- **S3 읽기**: 객체 하나를 읽을 때마다 worker의 AWS 신원을 다시 증명했다(새 SDK 세션, STS·IAM 호출 2회, 설정 기록). 객체당
  AWS 호출이 세 번이었다.
- **재검사**: 탐지가 없는 S3 객체는 캐시하지 않아 매일 전체 검사(RECONCILE)가 버킷 전체를 다시 내려받았다. 암호화 ZIP·크기
  한도 초과처럼 다시 읽어도 결과가 같은 추출 한계를 실패로 세어 기준선(watermark)과 마지막 전체 검사 시각을 막았고, 그 객체를
  매 실행 다시 읽었다.
- **기록 경로**: 요청마다 예산을 트랜잭션으로 잡고, 객체마다 진행 검증과 커밋을 했다. 읽기는 직렬이었다.
- **Notion**: 페이지마다 머리글 확인·Markdown·본문 뒤 재확인으로 요청이 3회였고, 페이지 작업이 하나씩이라 3개 fetch worker가
  한 페이지만 처리했다. 변경된 페이지만 고르는 경로가 없었다.
- **worker**: 컨테이너 하나가 작업 하나씩 처리했고, 긴 스캔 중에는 예약·변경 감지 폴링이 멈췄다. 같은 연결의 작업은 변경
  이벤트까지 모두 직렬이었다.
- **자동화 기본값**: 예약과 변경 감지가 기본 꺼짐이었다.
- **Slack**: 별도 설치형 SIEM 출력 패키지였다. 메시지에 이름·경로 없이 코드와 UUID만 있었고, 노출 심각도가 아직 없으면
  필터가 잘못 걸렀으며, 새로 켠 목적지는 보존된 과거 기록을 한꺼번에 보냈다.

## 3. 모든 소스에 공통인 경로

### 3.1 탐지기 고르기 (`2c99c9e2`)

모든 고유 키워드(소문자)를 긴 것부터 하나의 RE2 alternation(Latin-1)으로 묶어 내용을 한 번 검색한다. 매치 시작 위치 바로 다음
바이트부터 다시 찾으므로 시작 위치마다 가장 긴 키워드가 나오고, 그 안에 든 키워드(접두어 포함)는 미리 계산한 포함 관계로
채운다. 8바이트당 한 번보다 빽빽하게 매치되는 구간은 예전 방식으로 마무리하고, RE2가 없으면 예전 방식을 쓴다. 고른 탐지기 목록과
순서는 모든 입력에서 예전 `any(k in lowered for k in spec.keywords)`와 같고, 탐지 digest와 `ENGINE_EPOCH`는 그대로다.
측정(`scripts/bench_engine_routing.py`, 탐지기 목록 불일치 0): 저장소 파일 600개(약 7MB)에서 약 6.5배(2026-10-09)·10.2배
(2026-10-10, 4.18초 → 0.41초). 9MB 번들 스크립트 한 파일(`--bundle`, TypeScript `typescript.js` 9.07MB)에서 약 5.0~5.2초 →
0.13~0.15초(약 35~42배, 2026-10-09 측정은 4.30초 → 0.13초). 같은 머신에서도 측정마다 배수가 달라 범위로 적는다. 600개
말뭉치는 실행 시점의 저장소 파일이라 두 날짜의 입력이 같지 않다.

### 3.2 문서 형식과 바이너리 (`10b2c434`, `784486a2`)

- **POSIX fork 서버**: 파서를 미리 올린 작은 서버가 문서마다 자식을 fork해 주소 공간·core·CPU 한도를 걸고 읽는다. 서버는
  자식을 시간 한도에 죽이고(PARSE_TIMEOUT), 자기가 보내지 않은 신호로 죽은 자식은 PARSER_UNAVAILABLE로, 500문서·신호 종료·
  프로토콜 오류마다 서버를 교체하며, 다음 문서 전에 요청·응답 버퍼를 0으로 지운다. Windows는 문서마다 프로세스를 띄우는 기존
  경로다. Linux 컨테이너 측정(`scripts/bench_extraction.py`, 문서 60개, 결과 불일치 0): 문서당 약 4.3~4.5ms, 이전 방식
  308~441ms(약 70~98배). 2026-10-10 재측정 두 번 중 첫 번째만 서버가 문서당 10.3ms(약 42배)였다.
- **바이너리 문자열**: 알려진 형식이 아닌 제어 바이트 내용과 ELF·PE·Mach-O·Java class·SQLite는 8자 이상의 인쇄 가능한 ASCII와
  UTF-16LE 연속열을 검사한다. 그 안에 압축·PDF·암호화 표지가 있으면 미완료다.
- **옛 인코딩**: UTF-8이 아닌 텍스트는 CP949로 읽고, ASCII 바이트가 하나라도 사라지면 latin-1 읽기를 덧붙인다(cp1252 바이트가
  뒤 글자를 삼키는 경우). 제어 문자가 섞인 텍스트도 텍스트로 끝까지 읽는다.
- **옛 Office·HWP 3**: OLE 파일은 스트림마다 섹터 순서대로 읽는다. Excel 공유 문자열 표는 CONTINUE 레코드 경계에서 잘린
  문자열을 이어 붙인다(MS-XLS 2.4.265·2.5.293). 처음 구현은 파일 바이트를 그대로 읽어, 경계에 걸친 토큰을 둘로 끊고도 완료로
  보고했다. 커밋 뒤 감사에서 이를 찾아 고쳤고, 고치기 전 판독기는 합성 사례 9건(절단 위치 4곳×8비트/UTF-16, 흩어진 섹터 PPT)을
  모두 놓쳤다. 메모·텍스트 상자(TxO)의 글과 수식 문자열 결과(String)도 같은 방식으로 이어 붙인다(2026-10-11 추가).
  매크로·삽입 개체·압축 본문·암호화는 미완료, 손상된 디렉터리는 파일 바이트 문자열과 `MALFORMED_DOCUMENT`다.
- **미디어·미지원**: 오디오·비디오·글꼴·PSD·HEIC/AVIF는 미디어로 건너뛰고 zstd·LZ4·.Z·LZMA-alone은 미지원이다.
- **재검사 규칙**: 다시 읽어 결과가 달라질 수 있는 사유는 `PARSE_TIMEOUT`·`PARSER_UNAVAILABLE`뿐이다. `EXTRACTOR_EPOCH` 4로
  올라 배포 뒤 한 번 이전에 검사한 모든 루트를 다시 검사한다(9절).

상세 범위와 한계는 [공통 문서 스캔](DOCUMENT_SCANNING.md)에 있다.

### 3.3 런타임: 다시 읽지 않기, 묶어 쓰기, 겹쳐 읽기 (`55740eb9`)

- **결정적 한계는 실패가 아니다**: 재시도 대상이 아닌 추출 사유와 형식상 건너뛴 객체는 `failed_keys`·`objects_failed`에 넣지 않고
  기준선과 마지막 전체 검사 시각을 막지 않는다. 대신 `extraction_reasons`, `partially_inspected`와 루트 상태의
  `inspection_gaps`로 계속 보고하고 루트 커버리지는 완전이 아니다. 파서가 죽은 경우는 반복 재시도하지 않지만 캐시하지도 않는다.
- **탐지 없는 S3 객체도 캐시**: GET이 본 revision으로 저장하고, 행은 위치로 두고 조회할 때 revision을 비교한다(바뀐 객체도 행을
  지우지 않고 덮어쓴다). 형식상 건너뜀과 결정적 부분 추출도 캐시한다. 64개씩 한 번에 조회한다. 검증을 켠 실행도 탐지 없던 캐시는
  그대로 쓰고 탐지 있던 객체만 다시 읽는다.
- **예산·진행·커밋**: 요청 예산은 트랜잭션 한 번에 최대 64건씩 잡는다(한도는 넘지 않고, 중단되면 많게 셈). 진행 검증은 초당
  한 번이다. 탐지 없는 객체는 64개 또는 1초 단위로 묶어 객체별 효과를 그대로 한 트랜잭션에 쓴다.
- **겹쳐 읽기**: 캐시가 답하지 못한 객체를 다음 16개까지, 수집기의 `read_concurrency`(S3·ContentCollector 8)만큼 동시에 미리
  내려받는다(목록 다운로드와 합쳐 256MiB 이하). 읽기 스레드의 예산·요청 가드는 소유 스레드에서 실행하고, 추출·탐지·결과 저장은
  목록 순서대로 소유 스레드에서만 한다(S3 읽기 스레드는 요청마다 계정·승인을 확인하고 45초 신원 확인 기록을 남긴다). 오류·취소·예산
  중지는 모든 읽기를 취소하고 기다린다.
- 측정(`scripts/benchmark_worker_scan.py`, 메모리 저장소, GET 지연 20ms): 객체 308개 버킷의 첫 검사 3.32초(2026-10-10 재측정
  4.86초), 바뀐 것 없는 재검사 0.04~0.09초·내려받기 0회. 읽기 겹침은 텍스트 객체 96개의 별도 버킷에서 직렬 2.05~2.32초 → 겹침
  0.27~0.31초(두 번 모두 약 7.5배). 메모리 저장소 기준 상한이며 DB 왕복은 포함하지 않았다.

| Bitbucket Cloud·Data Center | 겹쳐 읽기 8개 | 증분 검사는 저장한 commit 이후 diff에 나온 파일만 읽음(파일 400개 중 1개 변경: 요청 411회 → 14회). 전체 검사는 최신 commit의 모든 파일을 다시 읽음 | diffstat·changes 피드 |
| Azure DevOps Git | 겹쳐 읽기 8개 | blob ID 캐시 | refs·diffs 피드, Service Bus |
| Azure DevOps TFVC | 겹쳐 읽기 8개 | 항목의 마지막 변경집합과 경로의 SHA-256으로 만든 revision 캐시(새로 추가) | 변경집합 피드(새로 추가) |
| Confluence | 첨부 8개 동시(공유 기본 주소를 바꾸지 않는 요청으로 바꿈) | 페이지 `<ID>:<버전>` revision 캐시(새로 추가, 라이브 문서는 제외) | CQL 변경 조회 |
| Notion | 페이지당 요청 1회(5절) | 수정 시각·검색 정보로 바뀌지 않은 페이지는 요청 없음 | 검색 변경 피드·공식 웹훅 |
| 회사 웹사이트 | 엔진·추출 공통 개선만 | - | 예약 검사 |

공급자 요청 제한: GitHub 보조 제한(403·429와 `Retry-After`, 남은 한도 0)과 502·503·504는 GET만 다시 시도한다. GitHub 보조 제한의
대기는 토큰을 쓰는 모든 읽기·프로세스가 함께 기다리며 최대 120초까지 기다린다. 쓰기 요청은 다시 보내지 않는다. GCP ADC·OAuth,
Azure 토큰, GitHub App, Atlassian 서비스 계정 토큰 갱신은 여러 읽기 스레드에서 한 번만 일어난다.

## 5. Notion 방식 대조

| 요청에 적힌 방식 | 요청 당시 코드 | 지금 |
| --- | --- | --- |
| 페이지 본문을 Markdown API로 한 번에 | 있음. 다만 본문 앞뒤로 머리글 확인 요청이 붙어 페이지당 3회 | 검색에서 미리 받은 페이지 정보(`page_meta`)가 있으면 Markdown 1회. 없으면 머리글 1회를 더. 본문 뒤 머리글 재확인은 없앴다: 실행의 기준선이 시작 시각이라 본문을 읽는 동안의 수정은 다음 증분 실행이 읽고, Notion 수정 시각이 분 단위라 재확인은 같은 분 안의 수정을 잡지 못했다 |
| 탐지된 페이지만 Block API로 다시 | 있음 | 그대로(위치 보강). 이때 머리글을 한 번 더 읽어 본문과 같은 revision인지와 지금의 주소·제목을 확인한다 |
| 3 worker 병렬 | 있음. 다만 페이지 작업이 하나씩이라 실제로는 한 페이지만 | 연결 하나의 페이지들을 한 실행에서 처리하고 요청은 연결별 제한기로 공유 |
| 초당 2.5회 제한 | 수집에만 있음 | 수집·계획·카탈로그·자격증명 점검·탐지 맥락·변경 피드·연결 마법사의 모든 Notion 호출이 같은 제한과 429·529 `Retry-After` 재시도를 씀. worker의 여러 프로세스는 DB 간격 행으로 함께 지킴(조치 실행 역할은 자기 프로세스 안에서만) |
| 첫 스캔 뒤 수정된 페이지만 | 기준선 비교는 있으나 페이지마다 머리글 요청이 필요 | 증분 실행은 5분 안에 받은 검색 정보로 수정 시각이 기준선보다 12분(검색 지연 10분·분 단위 반올림·시계 오차) 넘게 앞선 페이지를 요청 없이 건너뜀 |
| (없음) | 변경 페이지만 고르는 경로 없음 | 검색 변경 피드(`changes_since_batch`): 수정 시각 순으로 읽어 승인한 페이지 중 바뀐 것만 그 페이지 검사로 넣음(15분 겹침) |

`page_meta`는 실행의 계획 단계가 만든다(`9b95f585`). 전체·증분 실행은 승인한 페이지들의 머리글을 검색 한 번의 순회로 받아
각 페이지 작업에 그 페이지의 정보만 넘긴다. 순회 요청은 실행의 요청 예산에서 내고, 보내기 전에 계획 작업의 checkpoint에 예약해
계획이 다시 돌아도 덜 세지 않는다. 예산이 루트마다 한 번씩도 남기지 못하면 순회하지 않고, 순회가 실패하면 페이지마다 자기
머리글을 읽는다. 변경 스캔은 순회하지 않는다.

합성 측정(`scripts/benchmark_notion_markdown.py`): 500페이지 전체 검사 505회 요청(공유 5,000페이지 중 500페이지 승인이면 775회),
변경 5페이지 검사 11회. 시간(약 202초, 약 4.4초)은 요청 수를 초당 2.5회로 나눈 값이다. 탐지된 페이지의 블록 조회와 처리 시간은
빠져 있어 실제 시간의 하한이다. 요청에 적힌 실제 워크스페이스 측정(전체 4분 초반, 변경 30초 이내)은 재현하지 않았다. 검색 색인
지연이 12분을 넘는 경우는 12절에 적었다.

## 6. 무인 전체 스캔·공급자별 주기·변경 시 스캔 (`162a44fd`)

- **매일 전체 검사(기본 켜짐)**: 로그인한 사람이 없어도 worker 관리 프로세스가 5초마다 예약을 확인하고, 승인된 모든 범위를
  전체 검사(`RECONCILE`)한다. 설치 기본값은 하루 1번(`full_scan_default_minutes` 1440), 시작 시각 02:00 KST
  (`full_scan_start_minute` 1020, UTC 분)다. 범위마다 고정된 시각에 나눠 시작한다: 시작 시각부터 `min(4시간, 주기/2)` 안에서 범위
  ID로 정한 시각(기본 02:00~06:00 KST)이고 매일 같다(2026-10-12). 관리자는 **환경 설정 > 스캔 시작 조건**에서 하루
  1·2·3·4·6·8·12·24번 또는 끄기와 시작 시각을 고르고, 검사 대상마다 따로 정하거나 끈다(대상의 `full_scan_minutes` null은 설치
  기본값). 운영자 잠금 `SCAN_SCHEDULES_MODE=disabled`가 항상 우선한다.
- **슬롯과 중복 방지**: 전체 검사 슬롯 k는 시작 분 + k × 주기에 열린다. receipt를 슬롯이 시작한 시각으로 정해 여러 worker가 함께
  폴링해도 한 번만 접수하고, 시작 시각 변경 뒤에도 실행을 건너뛰지 않는다(업그레이드 때 이미 접수 시각이 지난 슬롯만 한 번 건너뛴다, 9절). 증분 슬롯은 항상 변경분(`DELTA`)만
  읽는다. 전체 검사 슬롯 시작과 함께(또는 그 뒤에) 열려 그 범위의 전체 검사 시각 뒤에 끝나는 증분 슬롯은 기다렸다가 그 전체 검사에
  합친다(분산 전과 같이 한 실행). 슬롯은 같은 profile 버전·승인의 전체 범위 실행이 답할 수 있다. 같거나 더 강한 예약 실행이 아직 대기 중이면 새 슬롯은 그
  실행에 합치고(`coalesced`), 관리자가 범위를 저장하며 넣은 첫 전체 검사나 슬롯 시작 뒤에 시작한 전체 검사(실행 중이거나 성공)도 그
  슬롯에 답한다. 반대로 저장과 첫 검사 사이에 예약 폴링이 전체 검사를 먼저 넣었으면 첫 검사 요청은 같은 승인의 그 예약 실행(대기
  또는 실행 중)을 돌려준다. 다만 예약 실행은 찾은 자격증명을 검증하지 않으므로, 검증이 켜진 설치(기본)에서는 검증할 요청에 이
  실행으로 답하지 않고 요청을 따로 실행한다. 첫 검사 요청에 다른 mode로 답하는 것은 이 예약 실행뿐이다(같은 mode의 대기·실행 중
  실행은 원래대로 답하되 요청보다 덜 검증하는 실행은 답하지 않고, 다른 승인의 예약 실행은 답하지 않는다). 자기 경로만 읽는 변경
  이벤트 실행과 finding 다시 검사는 어느 요청에도 답하지 않는다. 그래서 새 연동을 연달아 두 번 전부 읽는 것은 검증이 켜진 설치에서
  폴링이 저장과 첫 검사 요청 사이에 끼어든 경우뿐이다. 승인·연결 상태로 계획이 거절된 범위는 5분
  동안 다시 계획하지 않고(범위 행과 승인 시각별로) 슬롯도 소비하지 않는다.
- **공급자별 변경 시 스캔**: 공급자 API의 변경 조회기가 기본으로 켜져 있다. GitHub(브랜치 head 조건부 요청)·GitLab·Bitbucket·
  Azure DevOps Git·TFVC(새로 추가)·Confluence(CQL)·Notion(검색 변경 피드, 새로 추가)을 공급자별 간격(Bitbucket 15분, 나머지
  5분, 관리자가 변경)으로 보고 바뀐 파일·페이지만 그 정확한 경로로 검사(`EVENT`)한다. 바뀐 목록을 알 수 없거나 너무 길면 그
  루트의 변경분(`DELTA`), 이력이 다시 쓰였으면 처음부터(`BASELINE`) 읽는다. 바뀐 이름이 이벤트 검사에 거절되면(제어 문자, 4 KiB가
  넘는 경로) 그 루트의 변경분을 읽고 커서를 옮겨, 이름 하나 때문에 그 루트의 변경 감지가 멈추지 않는다. 객체 저장소는 고객이 승인한
  전용 큐(S3 → SQS, GCS → Pub/Sub, Azure Blob → Event Grid·Service Bus)로 받는다. 코드 저장소의 push 웹훅도 고객 큐로 전달받고,
  CreMore가 직접 받는 웹훅은 Notion 공식 웹훅이다. 새 연동은 "변경되면 검사"(`event_mode: ENABLED`)가 켜진 채 저장되고 마법사 마지막
  단계에서 끌 수 있다.
- **변경 조회가 다른 일을 막지 않음**: 조회기는 요청 제한(`SOURCE_RATE_LIMITED`)·서버 오류(`SOURCE_UNAVAILABLE`)를 기다리지 않고 다음 조회로 넘긴다.
  한 회차는 첫 조회부터 20초 안에서만 새 조회를 시작하고, 남은 루트는 다음 회차에 먼저 본다(`deferred`). 한 루트의 실패(대기열
  등록 실패·승인 거절)는 그 루트의 오류로 기록하고 그 루트의 간격 뒤에 다시 본다. 다른 루트는 계속 조회한다.
- **출처 기록**: 변경 이벤트 실행은 작업 payload의 `requested_by`(`feed`·`queue`·`webhook`)를 남기고, Slack 알림의 "검사 시작"이
  `변경 알림(피드)`처럼 출처를 적는다.
- **멈춘 전체 검사 이어가기**: 예산으로 멈춘 전체·증분 검사는 그 사이 같은 대상의 변경 이벤트 실행이 있어도 이어서 진행한다(변경
  이벤트 실행은 바뀐 것만 읽으므로 전체 검사의 이어가기를 대신하지 않는다).
- **화면과 운영 상태**: 설정 카드(설치 기본 주기·시작 시각), 검사 대상 편집기(하루 N번·끄기·설치 기본값), 온보딩 마지막 단계(전체
  검사 주기·"변경되면 검사")와 운영 상태·수집 실행의 다음 예정 시각이 같은 규칙을 쓴다.
- **업그레이드 주의**: 예약 검사·변경 조회기 스위치는 저장한 적 없는 설치와 이전 버전이 저장한 설정에서 켜짐으로 읽는다(이전
  버전은 무엇을 저장하든 모든 스위치를 꺼짐 기본값과 함께 기록해 그 `false`를 관리자의 선택으로 볼 수 없다). DB 이관(버전 14)이
  업그레이드 시각을 기록하고 그때 이미 접수 시각이 지난 전체 검사 슬롯은 건너뛰므로, 첫 예약 전체 검사는 그 뒤 처음 오는 범위별
  시각(기본 다음 날 02:00~06:00 KST, 그 시간대 안에 업그레이드하면 아직 오지 않은 범위는 그날)이다(9절).

## 7. 동시에 여러 곳이 바뀔 때: 병렬 스캔 (`308a9fc2`)

- **작업 프로세스 여러 개**: worker 컨테이너 하나가 관리 프로세스와 작업 프로세스 N개(`WORKER_CONCURRENCY`; 0이면 PostgreSQL에서
  쓸 수 있는 CPU 수와 4 중 작은 값, SQLite는 1; Helm 기본 2)로 돈다. 관리 프로세스는 작업을 맡지 않고 스캔과 상관없이 5초마다
  예약·변경 감지·고객 큐를, 60초마다 유지보수를 돌린다. 그래서 S3 스캔이 도는 중에 Notion이 바뀌어도 Notion 변경 스캔이 바로
  큐에 들어가고, 다른 작업 프로세스가 그것을 집어 함께 돈다.
- **공정한 작업 선택**: 우선순위 다음으로 이미 돌고 있는 작업이 적은 실행부터 고른다. 오래된 큰 실행이 다른 연결의 작업을
  막지 않는다.
- **같은 연결 안의 이벤트 레인**: 연결마다 실행 슬롯이 레인별로 하나다. 변경 이벤트로 시작한 실행(`scan_jobs.lane = event`)은
  진행 중인 전체·증분 스캔 옆에서 돈다. 같은 버킷·저장소·페이지는 여전히 한 번에 하나만 읽는다(`lock_key`). 스키마 기록 버전
  12가 인덱스를 바꾸며, 같은 연결·레인에 실행 중(`RUNNING`·`CANCELLING`) 행이 둘 이상이면 바꾸지 않는다.
- **장애 복구**: 죽은 작업 프로세스는 다시 띄우고, 30분 동안 응답이 없으면 교체한다. 모두 연달아 죽으면 상태 파일 갱신을
  멈추고 종료해 컨테이너가 재시작되게 한다.
- **긴 전체 검사가 변경 스캔에 길을 내줌(`9b95f585`)**: 같은 S3 버킷 루트의 변경 스캔이 진행 중인 전체·증분 검사 뒤에서
  기다리면, 그 검사는 지금까지 읽은 것을 커밋하고 checkpoint와 함께 대기열로 돌아간다(시도 수를 쓰지 않는 연기, 기다리는 작업마다
  한 번). 변경 스캔이 먼저 돌고, 검사는 마지막으로 커밋한 키 다음부터 이어간다. 시작 위치를 지나 처음 커밋한 뒤 5초가 지나야
  살피므로 이벤트가 계속 와도 검사가 매번 조금씩은 나아간다. 마지막 전체 검사가 3일 안에 끝까지 돈 루트에서만 양보한다. 양보한
  실행은 이어서 끝난 실행이라 제거 확정을 하지 않으므로, 첫 검사나 이벤트가 끊이지 않는 루트도 적어도 3일에 한 번은 끝까지 읽는다.
  양보 사이에 다른 실행이 기록한 미검사 사유도 잃지 않는다.

## 8. Slack 실시간 알림 (`5926dcf2`)

- **설정**: 콘솔 **환경 설정 > 스캔 시작 조건 > Slack 탐지 알림**(Admin). Incoming Webhook(받는 즉시 봉인, `hooks.slack.com`·
  `hooks.slack-gov.com` 서비스 경로만) 또는 연락 발송에 설정한 Slack 봇과 그 허용 채널. 최소 심각도·자세히/간단히·한국어/영어를
  고르고 시험 메시지와 전달 상태(대기 수·마지막 성공/실패·연속 실패)를 카드에서 본다. 이벤트 종류는 API(`events`)로만 고르고
  카드는 저장된 종류를 보여 준다.
- **누락 없음**: 새 노출·새 위치·제거 후 재노출 이벤트는 탐지를 저장하는 같은 트랜잭션에서 SIEM 대기열에 기록된다. 알림 채널은
  그 대기열을 목적지 `cremore.slack-alerts`로 읽고, Slack이 받았다고 답한 뒤에만 처리 완료한다(최소 한 번 전달, 이벤트 ID로 중복
  식별). 기준보다 낮아 걸러졌다가 기준 이상으로 오른 finding은 "심각도 상승"으로 알린다.
- **가벼운 회차**: 회차마다 커서 이후 이벤트에 한 문장(INSERT … SELECT)으로 전달 행을 만들고(알림이 될 수 있으면 받지 않은 행, 아니면
  보내지 않은 처리 완료), 받지 않은 행을 부분 인덱스 `siem_deliveries_owed`(스키마 기록 버전 13)로 찾는다. 30초마다 커서부터 전체를,
  그 사이에는 마지막으로 본 가장 새 이벤트 직전부터만 읽고, 늦게 커밋된 이벤트는 다음 전체 읽기나 한 시간마다의 전체 확인이 찾는다.
  SQLite에서 받지 않은 알림 뒤에 이벤트 10만 건이 있을 때 회차 약 17ms·상태 약 9ms, 5분 안에 이벤트 10만 건이 몰렸을 때 빠른
  읽기 회차 약 45ms였다(측정 조건은 [Slack 탐지 알림](SLACK_ALERTS.md)).
- **속도 제한·장애**: 설치 전체에서 1.1초에 한 통과 Slack의 `Retry-After`를 DB로 함께 지킨다. 4건 이상이면 최대 15건씩 묶는다.
  Slack 전체 장애(5xx·시간 초과·인증·채널)는 그 회차를 멈추고 보류 없이 지수 간격으로 다시 보낸다. 메시지 한 통만의 거절은 묶음을
  나누고 콘솔 버튼 없는 짧은 형태로 다시 보낸다. 회차는 임대가 끝나기 전에 멈추고 남은 알림을 시도 수에 넣지 않고 되돌린다.
- **보내는 곳(`9b95f585`)**: `5926dcf2`에는 발송 회차만 있었고 worker 연결은 이 커밋에서 들어갔다. 혼합(mixed) worker는 관리
  루프 옆의 자기 스레드에서, 역할을 나눈 배포는 control 프로세스의 자기 스레드에서 약 1초마다 한 회차를 돈다. 수집·조치 프로세스와
  작업 프로세스는 보내지 않는다. 트리거 폴링·유지보수가 오래 걸려도 알림이 늦지 않는다. 회차 자체가 예외로 끝나면(DB 권한·연결 같은
  문제) 예외 종류만 남기고 다음 회차를 두 배씩(최대 60초) 늦추며, 성공하면 1초로 돌아온다. Slack의 거절·장애는 회차 안에서 알림별로
  `min(3600, 5×2^시도 수)`초 뒤 다시 보낸다. 종료 신호를 받은 회차는 새 메시지를 시작하지 않는다(`d7a65055`). 보내던 한 통만 마쳐 ACK하고(최대
  15초 기다림), 가져온 나머지는 바로 돌려놓아 다음 프로세스가 임대(300초)를 기다리지 않고 보낸다(격리 Compose의 control
  `stop_grace_period` 30초). 멈춤은 관리 루프가 끝날 때 전해진다(control 프로세스는 최대 약 2초 뒤). 보내던 일이 15초를 넘기면(늦은
  Slack 응답, 거절된 메시지를 짧은 형태로 다시 보내는 중) 가져온 알림은 임대가 끝난 뒤 나가고 그 한 통은 두 번 갈 수 있다. control DB 역할에 전달 행·상태·간격 행 쓰기와 계정 이름 읽기 권한을, API 역할에 시험 메시지의 간격 행
  쓰기 권한을 더했다(역할을 나눈 설치는 `python -m cremore.db.privileges grant --schema cremore`를 다시 실행한다). 격리 배포의 control
  egress에 Slack 주소가 필요하다.
- **메시지**: 심각도·유형·발급 공급자·검증 상태·연결·리소스·위치와 줄·처음 발견 시각·검사를 시작한 것·다른 열린 위치 수·
  콘솔 상세 링크(`<콘솔 주소>/?view=exposed&id=credential%3A<UUID>`)·ID. 비밀값·가린 값·지문·공급자 응답은 넣지 않는다.
- 검증: 알림·SIEM·경로·보존·평가기·연락·마이그레이션 테스트(PostgreSQL 포함)와 독립 리뷰를 거쳤다. 세부 동작은
  [Slack 탐지 알림](SLACK_ALERTS.md)에 있다.

## 9. 바뀐 보안 경계와 운영 영향

- **S3 신원 재증명 간격(소유자 검토 대상)**: S3 내용 읽기에서 worker 자신의 AWS 신원 재증명은 계정마다 45초에 한 번과 역할
  자격증명을 새로 받을 때만 한다. worker 신원이 바뀌면 이전에는 다음 요청에서, 이제는 최대 45초 안에 읽기가 멈춘다. 계정·
  승인·revision·로그인 확인은 그대로 요청마다, 스트림 읽기 앞뒤와 결과 저장 트랜잭션 안에서 하므로 계정 비활성화·승인 철회는
  다음 요청부터 거절된다.
- **배포 직후 한 번 전체 재검사**: `EXTRACTOR_EPOCH` 4는 `detection_policy_digest`를 바꾸므로 이전에 검사한 모든 승인 루트에
  룰 변경 재검사가 들어간다. 그만큼 다운로드·추출 부하가 한 번 생긴다.
- **문서 파서 fork 서버**: 운영체제 sandbox가 아니다. 문서마다 새 자식 프로세스에서 읽고, 서버는 다음 문서 전에 버퍼를 0으로
  지우며, 자식의 메모리·CPU·core 한도는 그대로다. 다만 자식의 주소 공간에 미리 읽은 파서가 들어 있어 같은 한도에서 문서에 쓸 수
  있는 메모리가 약 40MB 적다([공통 문서 스캔](DOCUMENT_SCANNING.md)).
- **작업 프로세스만큼 메모리와 DB 연결**: worker 컨테이너 하나가 작업 프로세스 N개(Compose 기본은 PostgreSQL에서 CPU 수와 4 중
  작은 값)를 띄운다. 프로세스마다 스캔 중 최대 약 0.9GiB와 자기 DB 연결(읽기 스레드 수 + 2 정도)을 쓴다. 컨테이너 메모리 한도와
  DB 최대 연결 수를 이에 맞춘다.
- **캐시 행이 늘어남**: 탐지 없는 객체도 캐시하므로 검사한 객체마다 캐시 행이 생긴다. 오래된 행 정리 한도를 10만 행에서 200만
  행으로 올렸다(`ScanStore.prune_cache`, 14일). 큰 버킷을 검사하는 설치는 그만큼 DB 용량이 늘어난다.
- **알림 내용**: 메시지에 리소스 이름·경로·페이지 제목과 연결 이름이 들어간다. 알림 채널을 볼 수 있는 사람은 이 위치 정보를 본다.
  비밀값·가린 값·지문·공급자 응답은 들어가지 않는다.
- **업그레이드하면 매일 전체 검사가 켜짐**: 이전 버전이 저장한 설정은 관리자가 일부러 끈 경우도 켜짐으로 읽는다(이전 버전은 무엇을
  저장하든 모든 스위치를 꺼짐 기본값과 함께 기록해 둘을 구별할 수 없다). 그래서 잠그지 않은 모든 설치가 매일 02:00 KST부터 전체
  검사를 돈다(6절). 업그레이드 직후 한꺼번에 읽지 않도록, DB 이관(스키마 기록 버전 14)이 업그레이드 시각(`scan_schedule_origin`)을 DB
  시계로 한 번 기록하고 그 전에 승인된 범위는 그때 이미 접수 시각이 지난 전체 검사 슬롯을 건너뛴다. `EXTRACTOR_EPOCH` 4로 생기는
  정책 재검사도 전체 검사 주기가 있는 그 범위들에는 그 뒤 첫 전체 검사가 끝날 때까지(성공·부분·실패·취소 모두) 접수하지 않아, 첫
  전체 재검사와 epoch 재검사는 그 뒤 처음 오는 범위별 시각(기본 다음 날 02:00~06:00 KST에 나뉘어)에 한 번으로 겹친다. 그
  사이(전체 검사가 도는 동안 포함) 변경분 슬롯과 변경 이벤트 실행은 탐지 정책이 바뀌었다는 이유로 전체 읽기가 되지 않는다(S3·Notion은
  바뀐 것만 읽고, 캐시형 공급자의 변경분은 그 전체 검사로 미룬다, `policy_hold`). 새로 접수하는 실행은 업그레이드 뒤 48시간이 지나면
  보류하지 않는다. 전체 검사가 꺼진 범위는 바로 정책 재검사를 받는다. 업그레이드 뒤 관리자가 규칙을 바꾸면 보류를 끝내 바로
  재검사한다. 이 보류로 생긴 부분 실행은 운영 상태의 `JOB_PARTIAL`이나 연결 상태의 "일부 실패"로 세지 않는다.
- **control 역할의 권한이 넓어짐**: 알림을 보내려고 control DB 로그인이 SIEM 전달 행(`siem_deliveries`)과 목적지 상태를 쓴다. 이
  스키마는 행 수준 보안이 없어, control이 침해되면 외부 SIEM 목적지의 전달 행도 처리 완료나 재시도로 바꿀 수 있다. 이벤트
  원본(`siem_events`)과 감사 기록은 바꿀 수 없다([침해 이후 피해 제한](POST_COMPROMISE_CONTAINMENT.md)).
- **역할을 나눈 설치의 배포 작업**: 새 권한(control의 전달 행·상태·간격 행 쓰기와 계정 이름 읽기, API의 간격 행 쓰기)은
  `python -m cremore.db.privileges grant --schema cremore`를 다시 실행해야 생기고, control egress에 Slack 주소(`hooks.slack.com`·
  `hooks.slack-gov.com`·`slack.com`)를 열어야 알림이 나간다. 그 전에는 알림 회차가 권한·연결 오류로 실패하고(간격을 늘리며 재시도)
  이벤트는 대기열에 남는다.

### 9.1 업그레이드 순서

위 영향을 배포 순서로 모은 것이다. 일반 절차(쓰기 중지, 백업, migration, 같은 릴리스로 재시작)는
[기존 설치본 오프라인 업그레이드](SCANNING_IMPLEMENTATION.md#기존-설치본-오프라인-업그레이드)를 따른다.

1. **첫 전체 검사 시각을 확인한다.** 잠그지 않아도 업그레이드 직후 모든 범위를 한꺼번에 읽지 않는다. 그때 이미 접수 시각이 지난
   슬롯은 건너뛰고, 첫 전체 검사와 `EXTRACTOR_EPOCH` 재검사는 그 뒤 처음 오는 범위별 시각(기본 다음 날 02:00~06:00 KST, 시작
   시각부터 4시간 안에 나뉘어. 그 시간대 안에 업그레이드하면 아직 오지 않은 범위는 그날)에 함께 돈다. 그 시간대가 맞지 않으면
   배포 전에 콘솔의 시작 시각을 바꾼다. 변경 조회기까지 막으려면 새 버전을 띄우기
   전에 `SCAN_CHANGE_FEEDS_MODE=disabled`(Helm `scanning.changeFeedsMode`)를 설정한다.
2. **용량을 맞춘다.** Helm의 worker 메모리 한도 기본값은 3Gi다(작업 프로세스 2개가 동시에 큰 문서를 읽을 때 약 1.9GiB에 여유를
   더한 값). 작업 프로세스를 늘리면 하나에 약 0.9GiB를 더한다. PostgreSQL `max_connections`는 200으로 둔다. 연결은 작업
   프로세스 하나에 약 10(읽기 스레드 8, 본체, 임대 갱신), API pod 하나에 최대 15, 관리 루프에 몇 개를 쓴다. 기본 구성은 평소
   약 80, rolling update로 pod가 겹치는 동안 약 120으로 PostgreSQL 기본값 100을 넘을 수 있다(추정). Compose의 DB는 200으로
   띄우고, 외부 DB는 운영자가 설정한다.
3. **migration을 적용한다.** 이 변경분은 스키마 기록 버전 12(이벤트 레인 실행 인덱스), 13(Slack 전달 인덱스
   `siem_deliveries_owed`), 14(업그레이드 시각 `scan_schedule_origin`, DB 시계로 한 번 기록)를 더한다. 버전 12는 새 인덱스와 충돌하는
   실행 중 작업이 있으면 멈추므로 모든 writer를 멈춘 뒤 적용한다. 역할을 나눈 설치의 런타임은 14까지 이관되지 않은 DB에서 시작하지
   않는다(`DATABASE_MIGRATIONS_INCOMPLETE`).
4. **역할을 나눈 설치는** migration 뒤 `python -m cremore.db.privileges grant --schema cremore`를 다시 실행하고, control egress에
   Slack 주소(`hooks.slack.com`·`hooks.slack-gov.com`·`slack.com`)를 연다. control 컨테이너의 종료 대기는 30초 이상으로 둔다.
5. **배포 직후 확인한다.** 운영 상태의 worker 생존 신호, 환경 설정 > 스캔 시작 조건의 예약 검사·변경 감지 상태, Slack 탐지
   알림 카드의 시험 메시지와 상태 줄, 수집·탐지 현황의 다음 예정 시각과 진행 중인 전체 검사를 본다.
6. **설치 기본값을 고른다.** 하루 1번 02:00 KST(범위별로 06:00 KST까지 나뉨)가 맞지 않으면 환경 설정 > 스캔 시작 조건에서 주기·시작 시각을 바꾸거나 끈다.
   변경 조회기가 만들던 일일 전체 검사는 없어졌으므로, 예약 검사를 끄고 변경 조회기만 켜 두면 조회기가 놓친 변경을 잡는
   검사가 없다([변경 조회기](CHANGE_FEEDS.md#2-변경-조회기)). 운영자 잠금을 걸어 두었다면 원하는 때에 푼다. 풀면 그때 열려 있는
   슬롯의 전체 검사가 바로 접수된다.

## 12. 남은 한계와 미검증

- 실제 고객 계정·실제 Slack 수신·운영 DB 규모의 측정은 하지 않았다. 숫자는 합성 측정이다.
- macOS의 fork 서버 경로는 시험하지 않았다(Linux 컨테이너와 Windows만).
- Notion 검색 색인이 12분보다 늦게 반영되는 페이지는 증분 실행이 건너뛸 수 있다. 일일 전체 검사가 이를 다시 읽는다.
- 양보한 전체 검사가 이어서 끝까지 읽으면, 양보하기 전에 읽은 앞부분의 노출 위치는 `HEAD`로 하나씩 확인해 404인 것만 제거로
  확정한다(2026-10-11). 한 시도에 최대 1,000곳만 확인하므로, 앞부분에 열린 노출이 그보다 많은 루트는 나머지의 제거 확정이 다음에
  끝까지 읽는 검사(최대 3일)까지 늦어진다. 거절(403)이나 요청 제한으로 확인하지 못한 위치도 그때까지 열린 채로 남는다.
- 업그레이드 시각 기록(`scan_schedule_origin`) 행만 지우면(이관 버전 14 기록은 남은 채) 아무것도 건너뛰거나 보류하지 않고 평소대로
  검사한다(다시 기록하지 않는다). 버전 14 이전의 백업을 복원하면 다음 시작이 이관을 다시 거쳐 복원한 시각을 새로 기록하므로, 그때
  접수 시각이 지난 슬롯을 다시 한 번 건너뛰고 보류도 다시 걸린다(업그레이드와 같다). worker 시계보다 24시간 넘게 앞선 기록은 믿지 않고 경고
  로그(`SCHEDULE_ORIGIN_AHEAD_OF_CLOCK`)를 남긴다. 업그레이드 뒤 규칙을 바꿨다가 되돌려도 보류는 다시 걸리지 않는다(`rules_changed`).
  보류 중에는 변경 조회가 없는 캐시형 root(GitHub 등)의 바뀐 내용을 다음 전체 검사에서 읽는다(기본 최대 하루). 48시간과 규칙
  변경 뒤 약 1분의 보류 해제는 새로 접수하는 실행에 대한 것이고, 이미 `policy_hold`를 달고 대기·재개 중인 실행은 그 뒤에도 보류된
  채 돈다(새 정책을 확정하지 않으므로 뒤의 전체 검사나 정책 재검사가 다시 읽는다).
- Slack 알림의 상태 줄은 받지 않은 행과 커서 이후 아직 행이 없는 이벤트를 센다. 늦은 커밋을 기다리는 5분 구간의 이벤트도 세므로
  이벤트가 몰리는 동안 상태 조회가 조금 무거워진다.
- 실제 Bitbucket Cloud 요청 한도·실제 Notion 워크스페이스 색인 지연·실제 Slack workspace 권한은 확인하지 않았다.

### 13.4 보류 해제 시점·건너뛰기 기준 정리 (2026-10-12, `d19b0f0c` 기준 코드)

13.3 뒤에 남긴 한계 중 바로 고칠 것을 고쳤다: 보류가 첫 전체 검사의 접수가 아니라 끝(어떤 상태로든)에 풀리고, 업그레이드 때 이미
접수 시각이 지난 슬롯만 건너뛰며(`MAX_HOLD` 48시간), 이전 시도의 실패 목록이 넘친 보류 실행이 `RETRY_STATE_OVERFLOW`로
보고되고, "진행 중" 칸이 센 실행을 그대로 보여 준다. 접수 경계(48시간·약 1분)가 이미 접수된 보류 실행에는 적용되지 않는다는 점을
문서에 적었다.
