# 자격증명 대응 완료 기준 검토

기준: 2026-10-04, `integration/saas-structure`. 아래 v2 대응 회차를 구현했다.
기존 제거 확인을 새 조치 완료로 간주하거나 과거 이력을 소급 변경하지 않는다.

## 현재 확인한 구현과 실행 환경

- `governance/response.py`는 담당자에게 Slack·메일로 CreMore 링크를 보내고(회사 로그인 설치), 담당자는 회사 로그인 후 CreMore에서
  조치 결과를 보고한다. 로컬 설치는 운영자가 회신을 기록하고, 티켓 시스템 플러그인을 설정한 설치는 티켓으로도 보낼 수 있다
  ([소유자 승인과 대응 요청](TICKET_SYSTEMS.md)). 발송에 실패하면 링크를 무효로 만들고 다시 요청하게 하며 자동 재발송하지 않는다.
  지정된 담당자·요청 회차가 일치해야 응답을 받는다.
- 담당자의 응답과 구조화된 조치 보고를 함께 요구한다. 링크 응답은 보고 하나가 승인(완료)·거절(미완료·예외)을 함께 기록한다.
  `response_reports.py`가 현재 로그인 IdP의 수신자·유일한 이메일을 확인하며 티켓 시스템 회신은 정확한 티켓 응답 계정과 현재 매핑도 검사한다.
  외부 티켓의 임의 HTML 댓글은 저장하지 않는다. 기존 `Answer` 계약을 쓰는 모든 티켓 시스템 플러그인에 적용된다.
- 승인 응답 뒤 시작한 비교 가능한 스캔으로 노출 제거를 확인한다. `REMOVED`는 제거 증거이며
  키 폐기·교체·금고 보관을 모두 입증하는 상태가 아니다. `NEEDS_ACTION`의 후속 제거 확인도
  가능하므로, 기존 상태명은 보존한다. 새 회차는 `completion_version=2`이며 `COMPLETED`는 새 근거 평가만 만든다.
- `remediation/owner_approval.py`의 **키 조치 실행 전 승인**은 대응 완료 회신과 별도 계약이다.
  대응 회신으로 실행 승인·권한·직무 분리를 우회하지 않는다.
- 2026-10-04 GLPI 시험 연결로 서비스·별도 담당자 조회를 확인한 기록은 GLPI 제거(2026-10-12)로 현재 경로의 근거가 아니다.
  실제 사람에게 요청을 보내거나 그 사람의 보고·승인을 대신 제출하지 않았다. 실사용자 응답까지의
  실환경 검증과 fake 전송·어댑터를 사용한 자동 회귀 검증은 구분한다.

## 구현된 상태 흐름

| 사용자 표시 | 전환 근거 |
| --- | --- |
| 검토 대기 | 새로운 실제 노출 발생. 같은 자격증명 재탐지는 기존 항목의 위치·최근 관측을 갱신 |
| 검토 중 | 권한 있는 담당자가 명시적으로 `검토 시작` 실행. 단순 상세 조회·자동 새로고침은 상태를 바꾸지 않음 |
| 조치 중 | 대응 담당자 지정 후 티켓 발송 확인. 수신자 지정만으로 발송 성공을 추정하지 않음 |
| 조치 검증 중 | 정확한 담당자의 완료 회신과 필요한 조치 보고 수신. 재스캔·발급자·금고 근거를 확인 |
| 조치 완료 | 해당 회차의 완료 조건을 모두 충족 |
| 재조치 필요 | 완료 주장 후 노출 잔존, 이전 위치 또는 새 위치에 재출현, 필수 조치 불충족 |

발송 중·발송 결과 불명·조회 실패·회신 보완 필요는 위 단계에 딸린 진행 사유로 표시한다.
단계와 조회 권한은 별개다. 우연한 클릭·다른 팀의 참조 열람을 담당자의 업무 착수로 기록하지 않는다.
읽기 GET에 변경을 넣지 않고 기존 명시적 검토/배정·버전 검사·감사 계약을 확장한다.

## 완료 조건: AND와 OR

`조치 완료 = 담당자 완료 회신/보고 AND 평문 제거 확인 AND 해당 처리 경로의 자격증명 조치 확인`

| 처리 경로 | 추가로 필요한 확인 |
| --- | --- |
| 계속 사용하는 자격증명 | 새 자격증명 발급·안전한 금고 보관, 사용처 전환 보고/근거, 이전 노출 자격증명의 사용 종료 |
| 더 이상 필요 없는 자격증명 | 발급자가 제공하는 명시적 폐기·만료 등 사용 종료 근거. 폐기한 값을 금고에 새로 보관할 필요 없음 |
| 플랫폼이 검증하지 못하는 자격증명 | `증거 확인 필요` 유지. 담당자의 주장만으로 자동 완료하지 않음 |

평문 제거와 키 교체는 **AND**다. 노출된 키가 원래 금고에 있었다는 사실도 교체 필요성을 없애지 않는다.
노출된 기존 키를 그대로 금고로 옮기는 것만으로 이미 복사됐을 가능성을 해소할 수 없다.
계속 사용한다면 `새 키 발급 → 금고 저장 → 사용처 전환 → 이전 키 폐기`가 기본 순서다.
긴급 차단은 서비스 중단 영향을 고려한 별도 승인 절차를 사용한다.

폐기와 교체는 **업무 목적에 따라 고르는 경로**다. 모든 키에 폐기와 새 키 생성을 동시에 강요하지 않는다.
교체 경로에는 이전 키의 사용 종료가 포함된다. 단순 비활성화는 재활성화가 가능하므로 기본적으로
`차단 확인` 근거로 구분한다. 회전 호출 성공만으로 이전 버전·키가 사용할 수 없다고 단정하지 않는다.
API 권한 오류·네트워크 실패를 폐기나 만료 증거로 쓰지 않는다.

원문 없이 키 ID만 노출된 경우도 별도 분류가 필요하다. 현재 AWS PoC는 액세스 키 ID만 게시했으므로
메타데이터 연결은 가능하지만 Secret Access Key 노출 또는 값 지문 일치까지 증명하지 않는다.
이를 실제 비밀값 노출과 같은 자동 폐기 대상으로 취급하지 않는다. 오탐·정책 예외는 별도 근거와 승인으로
관리하고 정상적인 `조치 완료` 통계와 합치지 않는다.

## 금고 근거의 수준

- 같은 공급자·명시적 식별자·호환되는 HMAC 지문으로 연결한다. 이름 유사성으로 교체 관계를 만들지 않는다.
- 금고의 현재 값과 호환되는 **값 지문 일치**가 보관의 강한 근거다. 키 ID·Secret 이름·관리자 제출 위치만의
  일치, 과거 버전 일치, 공개 인증서 일치는 별도로 표시한다.
- 금고 미연결·범위 제외·권한 거절·부분 수집·오래된 수집은 `미확인`이다. `금고에 없음`으로 단정하지 않는다.
- 금고 보관 자체가 현재 발급자 유효성·사용처 전환을 증명하지 않는다. `읽기 권한이 안전하게 설정됨`이나
  다른 미연결 위치에 평문이 전혀 없음도 보관 일치만으로 단정하지 않는다.
- 금고 연동이 메타데이터만 읽는 구성이라면 자동 값 일치 판정은 불가능하다. 명시적으로 허용한 고객 측 수집기가
  메모리에서 지문을 계산해 보내거나, 별도 수준의 수동 근거로 남긴다. 완료 조건 때문에 값 읽기를 자동으로 켜지 않는다.
- 교체 뒤의 새 키는 옛 키와 다른 자격증명이다. 기존 승인된 교체 작업의 참조 또는 확인 가능한 발급자 근거로
  관계를 명시하고, 새 키를 실제로 노출시키는 방식으로 연결 정보를 만들지 않는다.

## 구체적인 담당자 회신

Slack·메일 링크로 받은 담당자는 CreMore의 링크 화면에서 보고를 제출하며, 그 보고가 응답(완료는 승인, 미완료·예외는 거절)을 함께
기록한다. 링크 화면은 회사 로그인의 확인된 이메일이 요청받은 담당자이고 사람 목록에서 아직 같은 활성 사용자일 때만 열린다.
팀 설치에서는 관리자도 다른 수신자를 대신해 보고할 수 없다. 로컬 1인 설치는 `기록` 회차에 운영자가 보고를 남기며
`LOCAL_OPERATOR_STATEMENT`로 별도 표시한다. 티켓 시스템 플러그인 회차에서 외부 승인만 먼저 도착하면 `REPORT_REQUIRED`로 남고,
CreMore 보고 폼만 먼저 제출하면 `WAITING_OWNER`를 유지한다.

필수 항목은 **처리 결과, 수행한 조치, 구체적 사유/방법, 수행 시각**이다. 계속 사용하는 키는
교체 작업/새 키의 비밀이 아닌 참조와 금고의 비밀이 아닌 위치도 받는다. 완료·미완료·예외 요청을 구분한다.
비밀번호·토큰·Secret Access Key·시크릿 본문은 받거나 보관하지 않는다.

티켓 댓글을 쓴다는 사실만으로 충분한 보고라고 판단하지 않는다. 빈 댓글·단순 Okay는 회신 보완 필요로 남긴다.
공급자 원문 JSON·HTML을 보관하지 않고 크기 제한, 텍스트 정규화, 비밀값 검사/거절을 거친 보고만 저장한다.
같은 로그인 IdP와 요청 수신자에 묶인 기존 보고 검증·불변 이력 저장을 티켓 회신과 CreMore 회신 폼이 공유한다.
사유는 담당자의 진술이며 스캔·발급자·금고의 검증 근거와 명확히 구분한다.

회신자, 티켓/승인 ID, 외부 응답 시각, 서버 수신 시각, 보고 내용의 고정된 버전/해시와 검증 실행 ID를
같은 회차·트랜잭션의 감사에 연결한다. 수정은 새 보고 이벤트로 추가하고 기존 응답·감사를 덮어쓰지 않는다.
민감한 보고 본문은 SIEM으로 자동 전송하지 않고 기존 최소 이벤트·감사 참조 계약을 유지한다.

## 동기화·재발견·기존 설치

- 목록, 상세, 대시보드, 처리 뱃지, audit/SIEM은 `credential_records`의 공통 상태 projection을 사용한다.
- 상세에는 조치 타임라인과 `회신 / 평문 제거 / 이전 키 종료 / 새 키 금고 보관` 체크리스트를 함께 표시한다.
- 대시보드 제목은 `자격증명 대응 현황`, 핵심 지표는 `조치 완료 / 대응 대상`이다.
  `평문 제거 확인`·`기존 키 종료 확인`은 검증 항목으로 남긴다. 문구만 바꾸어 기존 제거율을 완료율로 표시하지 않는다.
- 같은 키 재탐지는 총 자격증명 수에 누적하지 않는다. 제거된 노출 위치와 현재 노출 위치는 이력을 보존하며 구분한다.
- 새 노출 발생 시 완료를 재평가하고 `재조치 필요`로 돌린다. 회차별 멱등 키와 기존 티켓 참조로 중복 발송을 막는다.
  반복 스캔마다 새 티켓을 만들지 않는다. 기존 티켓 재개/후속 댓글이 가능한 어댑터만 이를 사용하고, 아니면 연결된 새 회차를 만든다.
- 실패·권한 거절·범위 축소·중지·기한 초과를 제거로 해석하지 않는다. 늦게 도착한 이전 회차의 결과로 최신 상태를 종료하지 않는다.
- 기존 `REMOVED`는 제거 이력으로 보존한다. 새 완료 기준의 버전을 회차에 고정하고 자동 소급 완료하지 않는다.
  완료된 시점의 증거는 남기되 이후 재노출·새 키 노출·검증 반전은 후속 이벤트로 처리한다.

## 구현 범위와 검증 순서

### 현재 검증 가능한 근거와 제한

- `coverage/response_evidence.py`는 저장된 근거만 읽는다. 승인된 AWS `DELETE_ACCESS_KEY`와 공급자
  `REVOKE_PROVIDER_CREDENTIAL`의 검증 완료, 또는 정확히 연결된 최신 완전 발급 목록의 명시적
  `REVOKED`/`EXPIRED` 상태를 사용 종료 근거로 쓴다. GitHub 조직 접근 철회는 전체 토큰 폐기로 인정하지 않는다.
- AWS 교체는 승인된 `PUBLISH_ACCESS_KEY_ROTATION`이 이전 키·새 키·불변 Secret 버전을 연결한다.
  같은 ARN·버전·새 키의 완전한 현재 값 관측을 별도로 요구한다. Publish만으로 기존 키는 종료되지 않는다.
- 다른 공급자는 담당자가 같은 발급 공급자·origin·tenant의 정확한 새 발급 항목을 목록에서 고른다.
  관계의 근거는 `OWNER_DECLARED_INVENTORY_REFERENCE`이며 공급자의 자동 교체 증명으로 표시하지 않는다.
  새 키의 호환 HMAC 또는 공급자 digest와 현재 금고 값 일치가 있어야 보관 확인을 통과한다.
  발급자가 값을 제공하지 않는 경우 식별자 선택만으로 보관 확인을 통과하지 않는다.
- 새 키가 현재 노출되어 있으면 교체 완료를 인정하지 않는다. AWS 새 키 검사 상한은 10,000 finding이며
  상한 초과도 검토 필요다. API가 제공하지 않는 종료·값 비교는 검증 필요로 남는다.
- 키 ID만 발견한 AWS 항목은 자동 완료하지 않으며 별도 예외/오탐 검토를 안내한다.
  실제 키 폐기·회전·금고 값 읽기는 이 기능이 자동 실행하거나 활성화하지 않는다.
- 보고는 UUID 멱등·CAS, 회차당 최대 100개 버전, 20개씩 이력 조회를 사용한다. 사유 20~2,000자,
  수행 시각과 고정 조치 선택을 검증하고 detector 및 안전한 텍스트 검사 후 저장한다.
- Worker는 약 1분마다 저장된 근거를 재평가한다(한도 있는 공통 비교 스냅샷을 만든 뒤 회차 처리 20초·최대 100회차, 다음 cursor부터 재개).
  새 스캔은 즉시 해당 회차의 제거/재발 상태를 기록한다. 완료 뒤 재발은 새 회차가 필요하며 자동 티켓 남발은 없다.
  새 보고 이후 다시 시작한 스캔을 요구하고 오래된 회차/버전으로 최신 결과를 덮어쓰지 않는다.
- 보고 본문과 검증 근거 스냅샷은 별도 immutable setting에 두고 hash·요청·회차 참조를 같은 트랜잭션의
  append-only 감사에 남긴다. SIEM은 기존 audit 참조·고정 상태만 보내며 본문·이메일은 보내지 않는다.
- 기존 회차는 v1 계약 그대로 남는다. 새 API/worker/web을 함께 배포한다. 되돌릴 경우 v2 상태를 해석하지
  못하는 이전 worker를 운영하지 않고 백업에서 복구하는 별도 절차를 사용한다.

기존 소유 계층을 확장한다: 연락 발송 링크·티켓 플러그인의 공통 Answer → 대응 회차 서비스 → 스캔·발급자·금고 근거 평가 →
공통 projection → 상세/목록/대시보드. 별도 DB 서비스나 공급자별 완료 판정기를 복제하지 않는다.

필수 회귀 검사는 응답 위조·수신자 변경·빈 사유·비밀값 유입, 같은 응답의 중복 처리, 늦은 스캔,
금고의 ID만 일치/과거 일치/부분 수집, 교체 후 기존 키가 아직 활성인 경우, 폐기해 재보관이 필요 없는 경우,
동시 재발견·재요청·worker 재시작이다. 실제 Slack 발송은 지정된 테스트 수신자로 별도 검증한다.

참고: [소유자 승인과 대응 요청](TICKET_SYSTEMS.md), [원문 없는 값 대조](UNIFIED_METADATA_CONTRACT.md).
