# API reference (`/api/v1`)

Route inventory from the FastAPI application, with scan contract notes below. The Next.js dashboard proxies `/api/backend/<path>` to `/api/v1/<path>`.

Authentication: `Authorization: Bearer <token>`. In `AUTH_MODE=local` the shared `API_TOKEN` is an admin; in
`AUTH_MODE=oidc` the token is an OIDC JWT verified against the issuer's JWKS and mapped to a role via the groups claim.
Roles are ordered `viewer < analyst < remediator < admin`; the **Role** column is the minimum required.

Raw secrets never appear in any response: credentials are served as fingerprints and masked `identifier_hint`s.
Scan-job reads expose status metadata only and explicitly omit the internal `payload`. There is no generic
`POST /api/v1/scan-jobs`; jobs can be created only through server-owned connection, catalog and approved-scope routes.
Every error response carries `detail` and `error` (the same reason). A refusal an
operator can reach -- a policy or state conflict (`409`), an expired cursor (`410`),
an unreachable dependency (`502`/`503`) -- begins with a stable `CODE:` the
dashboard localizes; the English sentence after it is what an API caller reads,
and a code the dashboard has no words for is shown as the server sent it.
Shape validation for a malformed request (`422`) stays plain English: the
dashboard never sends one. Any other `/api/v1/*` path answers `501` with
an explanatory `error` — the dashboard was designed for a wider contract; see the support matrix in
[ARCHITECTURE.md](ARCHITECTURE.md).

## Team activity audit

In `AUTH_MODE=oidc`, the API appends `API_REQUEST_STARTED` before a verified user's route or role gate runs,
then `API_REQUEST_SUCCEEDED`, `API_REQUEST_ACCEPTED` (HTTP 202), `API_REQUEST_DENIED` (401/403) or
`API_REQUEST_FAILED` with its HTTP result. Reads, exports, session checks and automatic dashboard polling are included.
These receipts supplement the existing domain events; a 202 does not mean the background job completed, and a start
without a result means the outcome is unknown. If the initial receipt cannot be written, the route does not run
(`503 AUDIT_RECORDING_UNAVAILABLE`). A failure to save the result also returns 503; a mutation may already have
completed, so examine its domain event before retrying. A process crash can leave only the start receipt.

`AUTH_SESSION_OBSERVED` records the first API use of verified session evidence: signed `sid`, else `auth_time`,
else token `iat`. This is **CreMore's observation**, not the IdP's authentication timestamp. Renewed tokens with the
same evidence do not repeat it. Deduplication survives API restart and concurrent requests through the existing
settings transaction, retaining the latest 32 evidence digests per subject; older evidence can be observed again.
No raw session ID or bearer is retained. Okta password/MFA failures and proxy logout occur before/outside the API
and remain in the IdP/proxy's audit system; frontend-only clicks without API requests are not server events.
Local shared-token installations keep their existing domain audit and cannot distinguish individual people.

Receipts use the existing append-only `finding_events`, writer MAC, worker hash chain and SIEM audit export.
The note is a versioned JSON envelope containing the verified subject's display name (200 chars), trusted email
(320 chars), role, HTTP method, registered route template, UUID path targets and status. Bodies, raw/free-form paths,
query strings, headers, tokens, provider responses and exception text are excluded. An unverified request's actor
is `UNKNOWN`; the API never uses unverified token claims to attribute it. Legacy domain events are not rewritten.

`GET /api/v1/audit` keeps its response shape and adds optional `actor_name`, `actor_email`, `actor_profile_basis` and `activity`
`{method, route, targets, status, role, session_basis}` for these receipts. Start/result rows share `target_id`
(the server-generated request UUID). The console shows the names and email, supports searching them, and displays
the request and HTTP result in the detail panel. It still loads the latest 1,000 rows; this limit does not delete
older stored evidence. Session/profile observation is prospective: historical logins cannot be reconstructed.
The latest verified name/email is also kept per exact subject in settings. Domain events, including older rows,
use this profile for display (`actor_profile_basis: CURRENT_SIGN_IN`); it is not a claim about their historical name.
Request/session snapshots take precedence (`EVENT_SNAPSHOT`). Subjects that have not been observed keep their IDs.
Display resolution never changes the event, actor ID, MAC, authorization, or digest-based matching.

## Routes

Provider auth methods with `new_setup: false` remain in the catalog for existing connections, but both creation
flows and a switch from another method reject them with `409 AUTH_METHOD_RETIRED_FOR_NEW_CONNECTIONS`.
Updating an existing owner's credential in that same method remains supported. AWS new setup additionally
requires an approved, automatically refreshed server workload identity; deployment outside AWS is supported
through the existing OIDC/web-identity path. A manual scanner-role setup remains available for unrelated
accounts that Organizations cannot enumerate.

GitHub App discovery binds each selected organization to its own installation token. A discovered enterprise
in `target.auth.github_enterprise` is an installation-management hint, not enterprise-wide collection consent.
The existing enterprise installer accepts this hint or an explicitly configured enterprise; v2 owners retain
all selected roots. Slack enterprise workspace discovery requires `admin.teams:read` and selected workspace
membership is rechecked before activation.

Every PUT under `/api/v1/settings/` that stores an installation setting (the switches above, scan triggers, auto-triage,
inventory manifests and the AWS settings), and an Admin's switch of a built-in detector, is recorded in the same
transaction as `INSTALLATION_SETTING_CHANGED` (target
`installation_setting`). The note names the setting and the fields whose value changed (`scan_triggers sqs_enabled=on
sqs_queue_url=set`): switches on/off, numbers as given, lists and maps by size, text set or cleared; never an address or
identifier. Only values validated to a closed set show as chosen: the auto-triage confidence ceiling, the CloudTrail
source, the Control Tower home Region and the change feed's minutes per provider (`change_feed_minutes=github:15`). A
request that changes no value (a screen saving its whole form unchanged) stores nothing and records nothing, and of the
settings one PUT names (the AWS investigations, Identity Center) only those whose value changed are stored; saving the
defaults shown for an AWS inventory setting that cannot be read rewrites it. Saves take turns, and a PUT that changes
some fields of a setting (scan triggers, auto-triage, the AWS organization and inventory settings) builds on the
setting as it read it: when another Admin saved that setting in between, it is refused with
`409 SETTING_CHANGED_MEANWHILE` rather than written over theirs. An Admin stopping a learned false-positive
profile or clearing its samples is
`LEARNED_FP_PROFILE_STOPPED` / `LEARNED_FP_PROFILE_RESET` (target `learned_fp_profile`).
The other settings keep their own audit rows (`CONTACT_DELIVERY_SAVED`, `TICKET_SYSTEM_SAVED`, `MACHINE_IDENTITY_CHANGED`,
`OWNER_APPROVAL_POLICY_CHANGED`, `DOMAIN_*`).

## Scan run contract

`POST /api/v1/scan-runs` accepts `plan_id`, `profile_version`, and optional `mode`
(`BASELINE`, `DELTA`, `RECONCILE`, or S3-only `INVENTORY`; default `BASELINE`).
A plan can be consumed once: identical retries return the existing run, while a
different mode returns `409`. A run is always queued, whatever else is scanning:
runs of different connections proceed at the same time up to the worker
concurrency, and within one connection a change-event run proceeds beside a sweep;
the same bucket, repository or page is never read twice at once. Preview expiry, profile version, current connection
authorization, and exact selected roots are validated. Workers recheck current
approval before provider requests and result writes; queue delay does not expire
an already admitted plan.

Coverage responses expose processing counters, `timings`, `reused`,
`skipped_archived`, `skipped_submodules`, `skipped_unsupported`, and stop reasons.
`count_basis=COMMITTED_OBJECT_ATTEMPTS` includes retry work, not distinct inventory
size. A completed task can still produce `PARTIAL` coverage. Inventory sets
`root_coverage_complete=false` and `coverage_basis=INVENTORY_REPORT_ONLY`.
`EVENT` and `POLICY_SWEEP` are internal trigger modes, not public run mode inputs.

Finding responses include nullable `all_locations_removed`. `true` means current
recorded locations were removed; it does not prove credential revocation and does
not automatically resolve the finding. `null` means presence has not yet been
recomputed for that historical finding.

The compatibility `/connections/{id}/scan` route uses the connection's full
configuration, not profile exclusions and budgets. Use approved scope runs for
fine-grained selection. See [the operator guide](SCANNING_IMPLEMENTATION.md) for
exact approval examples, HMAC headers/body, dedicated SQS, schedules, and offline
database upgrades.

## Bounded compatibility lists and private evidence

`GET /findings`, `/credentials`, `/exposure-surface`, `/governance/reviews`,
`/rotation-automation/jobs`, `/management-actions`, and `/management-actions/targets`
(under `/api/v1`) accept `limit` (default 200, maximum 500) and a UUID `cursor`.
They preserve their response body shapes and return `X-Page-Limit` and, when
another page exists, `X-Next-Cursor`. Pages use stable ascending record IDs;
finding severity sorting and filters apply within each page. Follow the cursor
even when a filter yields an empty page. Exposure-surface totals describe that
page. `/stats` aggregates all findings in SQL without loading each record.
`/tickets` retains its 50-item `offset`/`next_offset` contract, with the bound
applied in SQL. Finding summary pages reject more than 10,000 related exposures
or an 8 MiB serialized summary with 413; request a smaller page.

Public finding detail omits credential, component and session HMAC fingerprints;
internal evidence joins continue to use them. Viewer source/connection projections
show `configured` for external Vault references; only the Admin metadata
configuration read returns a validated editable `vault://` reference. Sealed
ciphertext and malformed legacy references are never returned. Triage notes are
limited to 500 characters and checked for credential-shaped values before state,
learning or append-only audit writes; assignment retains its 200-character limit.

Legacy rotation records cannot be converted into approval evidence: they lack a
plan hash and operational-review stamps. REQUESTED/PREPARED/FAILED records can
represent ambiguous writes and reserve their target against another rotation.
An administrator must reconcile the actual key and secret versions separately;
this API does not clear those reservations or retry legacy writes. Do not delete
or rewrite history to bypass them. New rotation uses separately approved
PREPARE/PUBLISH action plans and rechecks the current target allowlist at execution.
