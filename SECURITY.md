# Security Policy

## Post-compromise containment

Opt-in isolated deployments separate API admission, collection, remediation, control,
SIEM and migration credentials. See [the implementation and migration contract](docs/POST_COMPROMISE_CONTAINMENT.md).
Role checks in application code are not an RCE boundary. Separate keys, workload IAM,
database roles and enforced network policy limit the permissions of a compromised process.
They do not protect against host root, cluster administrators or compromise of the remediator's own write identity.
Runtime audit rows are append-only, but a process holding audit keys can forge new events;
independently retained anchors and provider audit logs remain necessary.

## Reporting a Vulnerability

Report suspected vulnerabilities privately through the repository host's private vulnerability reporting feature. Do not open a public issue for an unpatched vulnerability and do not include live credentials, customer data, or unnecessary exploit detail. If a downstream distribution does not provide a private reporting channel, contact that distribution's maintainers through its published security contact.

Maintainers should acknowledge a report privately, reproduce it against a supported version, coordinate a fix and credential/session revocation where required, and disclose only after operators have a remediation path.

## System and Scope

CreMore is a self-hosted security application. One installation is one administrative organization and one data-access trust boundary. It may connect multiple AWS accounts owned or administered by that organization, including accounts from more than one AWS Organization, but it is not a multi-tenant SaaS data plane. Organizations that do not share security administrators, identity policy, database access, and AWS trust should use separate installations and keys.

The security boundary covers the Python API and worker (`cremore/`), the detection engine and its sanitizer boundary (no raw secret leaves `SanitizedDetection`), the Next.js web application and server-side proxy, the PostgreSQL schema (`cremore/db/schema.py`), Helm deployment, container builds, and AWS CloudFormation onboarding templates. Collected secrets, including values read from GCP management APIs, exist only in collection memory; only keyed fingerprints and necessary metadata may persist. Reversible encryption and Base64 do not make collected secret storage acceptable.

Important assets include discovered credentials, sanitized finding evidence, installation-scoped fingerprint keys, OIDC tokens and role mappings, AWS role and External ID configuration, scan metadata, CloudTrail-derived usage evidence, and remediation audit history.

## Threat Model and Trust Boundaries

S3 object content, source-profile inputs and provider responses, object metadata and paths, detector output, API request bodies, OIDC claims before verification, CloudTrail fields, CloudFormation parameters, and imported rule data are attacker-controlled inputs. In a Helm install the browser boundary terminates at the authenticated Ingress. In a Docker Compose install it is the loopback-bound dashboard, whose server-side proxy attaches the shared local token only to requests whose Host header is a loopback name or an operator-listed `CREMORE_ALLOWED_HOSTS` entry. The API independently validates identity and authorization; it does not trust identity headers or UI visibility. Connected providers, AWS accounts, the OIDC provider, PostgreSQL, internal PKI, container registry, and Kubernetes control plane are separate external trust dependencies.

Security administrators are privileged but their actions remain authorization-checked and audited. A compromised scanned credential, malicious object, ordinary authenticated Viewer, or workload without the required role must not cross into another role, account, or installation boundary.

## Security Invariants

- Raw content-scan bytes, raw detector JSON, collected secret values, AWS secret access keys, and session tokens must never be persisted, logged, returned by an API, added to metrics, or included in audit metadata. Sanitization and bounded output handling occur before the detection durable-model boundary. The GCP value-storage exception, `store_values`/`keep_values` options, and admin raw-value endpoint have been removed. GCP value reads still support HMAC matching and private keyed change detection, including binary and empty payloads. A change requires compatible fingerprint scheme and key identity; these private fingerprints never appear in public responses or exports. Upgrading does not erase previously stored values or their backups: follow the [GCP cleanup procedure](docs/integration/GCP_TOTAL_GUIDE_KO.md#과거-원문-저장-설치의-이관), including backup, WAL and replica cleanup. This policy concerns collected secrets; credentials supplied to authenticate a provider connection retain the separate sealed-storage contract below.
- A connection stores bounded non-secret scope (bucket/prefix, owner/repo or org, workspace) and a `secret_ref`; the API rejects a connection config that carries secret-looking keys. `secret_ref` is either a `vault://` pointer or a token sealed with AES-256-GCM under a key derived (HKDF-SHA256) from `SEALING_KEY` (`sealed:v2:<key_id>:`, where `key_id` is a non-reversible HKDF name for the master that sealed it, authenticated with the ciphertext; `sealed:v1:`, which carries no key id, is still read). `SEALING_KEY` is unset by default and then derives from `FINGERPRINT_KEY`; setting it separates the two, so the fingerprint key -- which must never rotate -- stops being the master for stored tokens, and `SEALING_KEY_PREVIOUS` holds keys that may open a stored credential but never seal a new one. `SEALING_KMS_KEY_ID` plus `SEALING_KEY_CIPHERTEXT` move the master into AWS KMS, leaving only a ciphertext on the installation: recovering it needs `kms:Decrypt` on the named CMK, granted to the workload identity rather than to anything stored beside it, and that path is read-only wrapped so it can call `Decrypt` and nothing else. `SEALING_KEY_VAULT_PATH` instead reads the master from the configured KV v2 store; it is the one case where the API is wired into that store, because the API is what seals a credential an operator types in, and the deployment can give the API a role or token whose policy reads only that path while the worker keeps the one that reads connection references. The API never returns the token or its ciphertext; the worker opens it at scan time and holds the plaintext in memory for the job. Anyone holding both the database and the sealing key can decrypt stored tokens, so protect that key like the tokens themselves.
- Fingerprints use an installation-specific HMAC key supplied outside PostgreSQL. Separate installations must not reuse the key.
- There is no separate development or production mode. Start-up enforces what CreMore itself owns: a fingerprint key of at least 32 random bytes in every installation, no built-in API token (a shared local token must be at least 32 characters), an exact IAM role principal when onboarding is configured, and well-formed values. With `AUTH_MODE=oidc` the API independently verifies token issuer, signature, audience, expiry and subject. Transport (API TLS, database `sslmode`, issuer scheme), identity-provider group design and network policy are the installing organization's choice and are documented as recommendations.
- Provider verification of discovered credentials is on by default. An Admin switches it installation-wide from the dashboard; the change records who made it and applies from the next scan. `CREDENTIAL_VERIFICATION_MODE=disabled` locks it off regardless of the dashboard. Each check authenticates with the discovered credential against its documented provider endpoint.
- An OIDC installation requires a requester and a different approver for credential actions. A shared-token installation has one operator, who may approve their own action plan only after an explicit re-confirmation that is recorded as `self_approved`; such a plan cannot execute once the installation uses OIDC.
- Every API mutation and sensitive read is authorized on the server. UI hiding is not an authorization control. Viewer, Analyst, Remediator, and Admin permissions must remain separated.
- Browser clients never receive AWS credentials, database credentials, internal API tokens, connection tokens (sealed or plain), or the OIDC client secret. State-changing browser proxy requests require same-origin validation, and with shared-token authentication the proxy rejects any Host that is not loopback or listed in `CREMORE_ALLOWED_HOSTS` (DNS-rebinding defense; `X-Forwarded-Host` is not trusted for this decision).
- AWS member-role onboarding binds the intended 12-digit account, the Admin-approved runtime identity, unique External ID, partition, and configured role name. The approved identity is a stable principal, never an STS session: an exact IAM user or role ARN (no path wildcard), or an IAM Identity Center permission set trusted through the account root plus an `aws:PrincipalArn` pattern whose 16 `?` match only the reserved role suffix. Root credentials are refused, and approval requires the API and worker to report the same identity. Role validation runs in the worker and must prove the assumed identity belongs to the stored target account before it becomes scannable. When the worker's identity differs from the approval or its sign-in expires, AWS tasks are held rather than run.
- AWS investigations and key actions run only in the account they concern: the provider-verified key owner, the secret ARN's account and Region, or the account pinned on an action plan. Every request re-evaluates the account (enabled, organization facts, purpose-scoped validation under current revisions, approved identity match) and proves the session is in that account before use; the process's own identity is used only for an explicitly registered `RUNTIME_IDENTITY` account. Scanner and remediation access have separate approvals, revisions and validation results; results are stored compare-and-set under the revisions they were produced with. Only read-only scanner STS credentials are cached. Rotation is refused before any AWS write outside the `RUNTIME_IDENTITY` account, and PUBLISH requires the authorization PREPARE ran under. Evidence collected before account provenance was recorded is shown as unverified.
- Scanner and remediation privileges remain separate. Remediation is disabled by default, destructive deletion requires an explicit deployment policy, every action is audited, and remediation alone never marks an exposure resolved.
- Exposure absence requires a fully read current object or authoritative complete in-scope listing. Notion search omissions/404, legacy collector epochs, delayed Inventory and events alone never prove absence. Removing an exposure never automatically resolves the credential finding; rejected verification is not revocation proof. Failed, skipped, capped and unsupported coverage remains partial.
- Passive cache reuse is connection/source-root scoped and bound to revision and detection digest; current path policy, risk and false-positive rules must be reapplied. S3 watermark filtering retains overlap and failures and requires periodic full reconciliation. Unknown state triggers content reads, never a clean inference; reuse is reported separately from coverage gaps.
- Scan clients allow exact read operations and source IAM policies explicitly deny writes. Event adapters authenticate before admission, consume only an operator-confirmed dedicated SQS queue, and acknowledge only durable jobs; they never provision or rewrite source infrastructure. Scan-scope approval is not authorization to create cloud resources or change source permissions.
- Result, reconciliation and checkpoint writes require current task lease ownership. Offline identity migrations require all API, worker and other writers stopped and a restorable database backup; migration archives supplement but do not replace that backup.
- Scan paths, failed-key lists, masked detection caches, Inventory comparison metadata and migration archives are sensitive data even without raw credentials. Keep them inside the installation trust boundary, bound processing/storage and protect backups and temporary directories. Hash-based identity keys are not path encryption.
- False-positive learning is account/source/detector/credential-type scoped, requires the configured minimum independent confirmations and similarity threshold, remains explainable and audited, and fails open as a security finding on classifier error.
- Observed use, inferred relationships, and IAM-policy potential access remain distinct evidence layers. Potential permission must never be presented as observed credential use.
- Network access, parsing, object size, process output, concurrency, query result count, and scan temporary storage remain bounded. Default-deny workload networking and least-privilege AWS identities are strongly recommended for every installation.

## Reportable Findings and Severity Context

Reportable issues include authentication or RBAC bypass; cross-account or cross-installation data access; raw-secret disclosure or retention; confused-deputy role assumption; unapproved external verification or egress of scanned content; unsafe CloudFormation account binding; unauthorized or unaudited remediation; coverage states that falsely claim a successful clean scan; evidence-layer confusion that materially understates blast radius; unbounded attacker-controlled parsing or resource consumption; and supply-chain changes that bypass pinned-source, vulnerability, provenance, signature, or license controls.

Treat remotely reachable identity bypass, raw credential exposure, cross-account role assumption, and unauthorized credential deletion as critical or high depending on realistic reachability and impact. Do not lower severity solely because a UI hides an action, a test uses placeholder data, or an intended infrastructure control has not been verified in the affected deployment.

## Out of Scope and Accepted Boundaries

- Placeholder credentials and synthetic identifiers in tests and documented examples are not findings unless they are usable or can be confused with production material.
- Docker Compose is the single-operator installation for a security officer's own computer: ports are published on loopback only, traffic between its containers stays on the host, and a shared local token authorizes the dashboard as Admin. Anyone who can run processes as a user on that computer can therefore use the dashboard; run it on a personal workstation, not on a shared multi-user host. Plain HTTP on loopback and the absence of per-user roles are accepted for this installation. Reaching the dashboard from another origin or host (for example DNS rebinding, a non-loopback Host header, or cross-site requests) remains reportable.
- Missing dashboard persistence for a profile source, secret-manager inventory scanning, archive extraction, or resource types outside the documented release scope is a feature limitation, not a vulnerability. A false claim of coverage remains reportable.
- Vulnerabilities in upstream dependencies (FastAPI, SQLAlchemy, boto3, httpx, Next.js, oauth2-proxy, etc.) should be reported upstream unless the platform's pinning, invocation, packaging, or isolation makes the impact specific to this project.

There are no blanket accepted-risk exclusions for injection, authorization, cryptography, credential handling, dependency, or denial-of-service findings.

## Known Limitations and Compensating Controls

The platform is not application-level multi-tenant. Deployment separation, distinct databases, distinct fingerprint keys, distinct OIDC clients/groups, and distinct workload identities are required between independent organizations. IAM potential-access simulation is intentionally curated and is not a complete effective-permission proof. Connection capability projections shown in the dashboard are administrator declarations, never probes: nothing touches a provider except a queued scan job. The dashboard support matrix in `docs/ARCHITECTURE.md` lists which panels this API implements; unimplemented paths answer `501`.

The compatibility connection-wide scan API uses the connection configuration, not an approved profile's path exclusions and budgets; use approved scope runs for fine-grained selection. Current-state scans do not comprehensively inspect Git history or old S3 versions. Inventory is delayed, possibly filtered report-only coverage and does not advance a normal root watermark. The optional HMAC endpoint accepts normalized CreMore events, not native GitHub/Notion webhook protocols. A provider adapter must validate the original provider signature before transforming it. No source notifications, Inventory configuration, CloudTrail selectors, EventBridge rules or queues are automatically created or overwritten. These limitations never justify falsely clean coverage or credential-revocation claims.

The detection engine is the project's own Python implementation (Apache-2.0); no third-party secret-scanning executable or detector catalog is redistributed. oauth2-proxy is rebuilt from hash-verified MIT-licensed upstream source with a documented dependency-only security update. Public distributors must preserve the notices and obtain their own legal review.
